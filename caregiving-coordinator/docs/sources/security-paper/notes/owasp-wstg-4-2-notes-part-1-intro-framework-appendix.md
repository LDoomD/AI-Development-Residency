### Foreword and frontispiece

| What the pages say (my words) | Section or test ID |
|---|---|
| The foreword says OWASP wants insecure software to be the exception. It argues testing should follow "engineering and science": consistent, repeatable and defined. | 0-Foreword, opening and "Why OWASP?" |
| Security testing alone is not a good measure of how secure an app is. There are endless ways to break an app and nobody has time to test them all, so "we can't hack ourselves secure." Testing is one part of a wider approach to building a secure system. | 0-Foreword, paragraphs 3-4 |

### Introduction (chapter 2)

| What the pages say (my words) | Section or test ID |
|---|---|
| The project aims to answer the what, why, when, where and how of testing web apps. It gives a whole framework, not only a checklist, so organizations can build their own testing program or judge someone else's. It tried to move web-app testing away from only penetration testing and toward testing built into the software development life cycle (SDLC). | 2-Introduction, "The OWASP Testing Project" |
| Measuring security is hard. Few technical people can turn a weakness into a dollar cost, and until they can, leaders cannot size security budgets. The guide cites a 2018 estimate of about $2.84 trillion for the cost of poor-quality software in the US (a software-quality group's figure, not a measure of security alone). | 2-Introduction, "Measuring Security: the Economics of Insecure Software" |
| "Testing" here means comparing the state of a system against a set of criteria. The guide says many outsiders see security testing as a "black art" because people test against mental criteria that are not well defined, and it aims to make testing doable by people without deep security skills. | 2-Introduction, "What is Testing?" |
| Most people only test after the app is built and deployed, which is ineffective and costly. A better way is to add security to every phase of the SDLC. The figure shows an estimated rising cost of fixing bugs later (figure not viewed). | 2-Introduction, "When to Test?" |
| Test people, process and technology, not only the software. Education and awareness (people), policies and standards (process), and the technology result. Testing only the technical side misses management and operations problems and gives an incomplete picture. | 2-Introduction, "What to Test?" |
| Each test has an ID in the form `WSTG-<category>-<number>` (for example WSTG-INFO-02). Because IDs can change between versions, the guide says to cite `WSTG-<version>-<category>-<number>` (for example WSTG-v42-INFO-02) and to use versioned links, not "stable" or "latest". This matters for the paper's own citations. | 2-Introduction, "How To Reference WSTG Scenarios" and "Linking" |
| Principle: there is no silver bullet. Scanners and web application firewalls help find "low-hanging fruit" but are generally immature and weak at deep testing. "Security is a process and not a product." | 2-Introduction, "Principles of Testing", "There is No Silver Bullet" |
| Principle: think strategically, not tactically. The old "patch-and-penetrate" habit fixes a reported bug without finding the root cause. The window between a flaw being found and an automated attack on it keeps shrinking, so build security into the SDLC and use threat modeling to direct effort to the riskiest parts. | 2-Introduction, "Think Strategically, Not Tactically" |
| Principle: "The SDLC is King." Add security to each phase (define, design, develop, deploy, maintain) of whatever process the team already uses. The text names BSIMM as a descriptive secure-SDLC model, and OpenSAMM and ISO/IEC 27034 as prescriptive ones. Prescriptive shows how it should work; descriptive shows what organizations do. | 2-Introduction, "The SDLC is King" |
| Principle: test early and test often. A bug found early is faster and cheaper to fix. Train developers and QA to think like an attacker. | 2-Introduction, "Test Early and Test Often" |
| Principle: test automation. In agile, DevOps or DevSecOps work, put security tests into the CI/CD pipeline, using DAST (dynamic scanning), SAST (static code scanning) and SCA (dependency and library checking), either at each release or on a schedule. This gives a baseline and catches easy problems. | 2-Introduction, "Test Automation" |
| Principle: understand the scope of security. Classify what you protect and handle each class accordingly, and talk to legal counsel about legal requirements. The guide gives US examples (Gramm-Leach-Bliley Act, California SB-1386) and EU examples (a 1990s directive and the GDPR, which it says require due care with personal data). It does not list HIPAA here. | 2-Introduction, "Understand the Scope of Security" |
| Principle: develop the right mindset. Good testers think beyond normal use, look for assumptions developers made, and try to break them. Tools do not think creatively. | 2-Introduction, "Develop the Right Mindset" |
| Principle: understand the subject. Keep accurate documentation (architecture, data-flow diagrams, use cases), including disallowed use cases, and have basic monitoring of attacks. | 2-Introduction, "Understand the Subject" |
| Principle: use the right tools, but know what they can and cannot do. Principle: the devil is in the details: a shallow review gives false confidence that is as dangerous as no review, and false positives must be removed because wrong findings weaken a report. | 2-Introduction, "Use the Right Tools" and "The Devil is in the Details" |
| Principle: use source code when available. Black-box testing cannot reach the whole code base, and some flaws only show in the source. | 2-Introduction, "Use Source Code When Available" |
| Principle: develop metrics. Track results over time to see whether training is needed, whether a mechanism is misunderstood, and whether total problems are falling. Document the test results: who did what, when, with what findings, in a format useful to developers, managers, business owners, IT, audit and compliance. The report should let a second tester reproduce results. A template saves time. | 2-Introduction, "Develop Metrics" and "Document the Test Results" |
| Four techniques are described. (1) Manual inspections and reviews: people reviewing policy, documents and design, with a "trust but verify" stance. Good for testing the SDLC process itself. Slow and needs skill. (2) Threat modeling: a risk assessment for an app. Steps, following NIST SP 800-30: decompose the app, classify assets, explore vulnerabilities, explore threats, create mitigations. Do it early and revisit it. A good threat model does not automatically make good software. | 2-Introduction, "Testing Techniques Explained", "Manual Inspections and Reviews", "Threat Modeling" |
| (3) Source code review: the guide says there is "no substitute for actually looking at the code". It is best for concurrency problems, flawed business logic, access control problems, crypto weaknesses, backdoors and missing input validation. Drawbacks: needs skilled reviewers, can miss issues in compiled libraries, cannot easily find runtime errors, and the deployed code may differ from the reviewed code. (4) Penetration testing: testing a running app from outside like an attacker. Fast and tests what is exposed, but it is "too late" in the SDLC and, in the guide's words, can find only a small sample of the risks. It is best used to confirm known issues were fixed. | 2-Introduction, "Source Code Review" and "Penetration Testing" |
| Use a balanced approach: all techniques across all SDLC phases, with more effort early (Figures 2-3 and 2-4, not viewed). Penetration testing alone is "too little too late." If you have no source code, pen testing is better than nothing, but challenge that assumption. | 2-Introduction, "The Need for a Balanced Approach" |
| Automated scanners have a place but real limits. Example 1 ("Magic Parameters"): a secret 30-character admin backdoor value that a scanner would need trillions of guesses to find, but that is obvious in the code. Example 2 ("Bad Cryptography"): a home-made sign-on token built from an MD5 hash of a username and date, which a code review spots at once but a scanner sees only as random-looking data. The OWASP Benchmark Project measures how well such tools perform. Static code scanners cannot find design flaws and need heavy manual checking. | 2-Introduction, "A Note about Web Application Scanners", "Example 1", "Example 2", "A Note about Static Source Code Review Tools" |
| Security test requirements come from three places: laws, regulations and standards (it names FFIEC for banks and PCI DSS for card data as examples), "positive" requirements (what the app must do), and "negative" requirements (what it must not do). Test objectives are two: check that controls work as designed (confidentiality, integrity, availability), and check that they have few or no vulnerabilities (for example the OWASP Top Ten). | 2-Introduction, "Deriving Security Test Requirements", "Testing Objectives", "Security Requirements Documentation" |
| Threats can be sorted with STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). A root cause can be a design flaw, a coding bug, or insecure configuration. Rate each vulnerability by severity so that high and medium ones are fixed first and low ones can wait. Keep a vulnerability knowledge base to measure how well tests work. | 2-Introduction, "Threats and Countermeasures Taxonomies" and "Security Testing and Risk Analysis" |
| Positive requirement examples: lock the account after a set number of failed log-ins, require minimum password length, mask confidential data, show generic login errors, make password reset one-time. Negative requirements ("do not allow data to be altered or destroyed") are harder to test because there is no expected behavior, so they should be driven by threat modeling and attack trees (for example "attacker reads other users' messages"). | 2-Introduction, "Functional Security Requirements" and "Risk-Driven Security Requirements" |
| Use cases and misuse (abuse) cases: write what the app should do and how an attacker could abuse each step, then turn the countermeasures into requirements. The worked example is authentication: brute force and account guessing lead to requirements for strong passwords, lockout after five failed attempts, and generic login errors. | 2-Introduction, "Deriving Security Test Requirements Through Use and Misuse Cases", Steps 1-4 |
| Security testing in the workflow: developers run static analysis and security unit tests (adapted from JUnit, NUnit and CUnit style frameworks) on their own code. Testers then run integrated system tests (white-box, black-box and gray-box). Findings go through defect tracking, a senior developer reviews code before merge, and high-risk issues must be fixed or formally accepted before deployment. Unit tests should cover identity and access control, input validation, encryption, user and session management, error handling, and auditing and logging. A check-in gate can block code with high or medium coding issues. | 2-Introduction, "Security Tests Integrated in Development and Testing Workflows", "Developer's Security Tests" |
| Integration tests check "defense in depth", meaning controls at more than one layer. The first place to simulate real attacks is the integration environment. A user-acceptance test (UAT) environment is closest to production (but with fake data) and is the place to check configuration: least privilege, valid certificates, unneeded services disabled, test and admin pages removed from the web root. A "security test cases cheat sheet" can let less specialized testers do a first round of common checks. Deeper work uses fuzz testing, fault injection and reverse engineering. | 2-Introduction, "Functional Testers' Security Tests" |
| Metrics: use goals with numbers and dates (the example is "reduce vulnerabilities by 30%"), compare to a baseline, and track "containment" (how well each phase catches issues in that phase, since fixing later costs more). Example questions the data can answer: are vulnerabilities low enough to release, what are the main root causes, which activity finds the most. The guide warns that unknown issues are not tested, a clean result "does not mean that the software or application is good", and automated results alone give a false sense of security. Hire skilled people as well as tools. | 2-Introduction, "Security Test Data Analysis and Reporting", "Goals for Security Test Metrics and Measurements" |
| What a good finding record has: vulnerability type, threat, root cause, test technique used, fix, and severity (CVSS from FIRST is named as the most common score). It should also tell developers how to re-test. The fix advice should be detailed, with examples. | 2-Introduction, "Reporting Requirements" |
| Business cases by role: developers (justify tools and training), project managers (track schedule), security officers (show testing does not slow delivery), auditors (assurance), and CIOs and CISOs (cost-benefit and return on security investment). The only reference is a 2002 NIST study of the cost of inadequate software testing. | 2-Introduction, "Business Cases" and "References" |

### The testing framework (chapter 3)

| What the pages say (my words) | Section or test ID |
|---|---|
| The framework is a reference model of tasks for different SDLC phases. It is not prescriptive, and teams should mold it to their process. It is aimed at organizations building a strategic testing process, not at consultants doing narrow tactical tests. The cost argument cites a book that says a security bulletin costs Microsoft at least $100,000, with customers paying more (an old figure from a 2004 book listed in Appendix B). | 3-The_OWASP_Testing_Framework, `0-The_Web_Security_Testing_Framework.md`, "Overview" |
| It says penetration testing is generally inefficient at finding bugs and depends too much on tester skill. It should be an implementation check or a way to raise awareness, and software security quality is improved by testing in all stages. | same file, "Overview" |
| **Phase 1, before development begins:** 1.1 define an SDLC with security at each stage; 1.2 review policies and standards (people can only do the right thing if they know what it is; for example a Java coding standard, or a cryptography standard if crypto is used); 1.3 plan measurement and metrics and keep traceability. | same file, "Phase 1.1", "1.2", "1.3" |
| **Phase 2, during definition and design:** 2.1 review security requirements, and test the assumptions in them (the example asks whether "registered" means registered or signed in). Mechanisms to check for gaps: user management, authentication, authorization, data confidentiality, integrity, accountability, session management, transport security, tiered system separation, and legal and standards compliance including privacy. 2.2 review design and architecture. Design flaws are cheapest to fix, such as one central authorization component instead of authorization checks in many places, or one central input-validation framework. 2.3 build and review UML models. 2.4 build and review threat models, and decide whether each threat is mitigated, accepted by the business or handed to a third party such as an insurer. | same file, "Phase 2.1" to "2.4" |
| **Phase 3, during development:** 3.1 code walkthrough with developers (high level, to understand structure; not yet a review). 3.2 code reviews against checklists: business needs for availability, confidentiality and integrity; OWASP Top 10; language and framework issues; and industry rules (the guide lists Sarbanes-Oxley 404, COPPA, ISO/IEC 27002, APRA, HIPAA and Visa merchant guidelines). The guide says static code reviews give far better returns than other review methods and depend least on reviewer skill, but are "not a silver bullet." | same file, "Phase 3.1" and "3.2" |
| **Phase 4, during deployment:** 4.1 application penetration testing after deployment as an extra check. 4.2 configuration management testing: check how the infrastructure was set up so nothing is left at a vulnerable default setting. | same file, "Phase 4.1" and "4.2" |
| **Phase 5, during maintenance and operations:** 5.1 operational management reviews (a documented process for running the app and infrastructure); 5.2 periodic health checks, monthly or quarterly; 5.3 change verification, meaning after each approved change goes to production, check that the security level did not drop, built into change management. | same file, "Phase 5.1", "5.2", "5.3" |
| A "typical SDLC testing workflow" figure (Figure 3-1) closes the chapter. I saw only its caption. | same file, "A Typical SDLC Testing Workflow" |
| The chapter's index page lists the five phases, the workflow figure, and a section on penetration testing methodologies. | 3-The_OWASP_Testing_Framework, `README.md` |
| Other published methods the guide points to: OWASP's own guides (web, mobile and firmware); PTES (7 phases: pre-engagement, intelligence gathering, threat modeling, vulnerability analysis, exploitation, post exploitation, reporting); the PCI penetration-testing guidance (tied to PCI DSS Requirement 11.3: industry-accepted approach, covers cardholder-data environment and critical systems, external and internal tests, application-layer and network-layer tests); the Penetration Testing Framework (network, server, wireless, physical and more); NIST SP 800-115 (review techniques, target identification and analysis, vulnerability validation, planning, execution, post-testing); and OSSTMM (operational security, human, physical, wireless, telecom, network testing, reported in a "STAR" report). The text says OSSTMM can support ISO 27001 but is not a hands-on technical guide. The references include a 2012 HIPAA security-testing presentation from NIST staff. | 3-The_OWASP_Testing_Framework, `1-Penetration_Testing_Methodologies.md`, all headings and "References" |

### Web application security testing introduction (chapter 4, section 4.0 only)

| What the pages say (my words) | Section or test ID |
|---|---|
| Definitions used by the guide. Security test: methodically checking whether application security controls work, through active analysis for weaknesses, flaws and vulnerabilities, with findings given to the owner along with impact and a fix. Vulnerability: a flaw or weakness in design, implementation, operation or management that could be exploited to compromise security goals. Threat: anything (outside attacker, insider, system instability) that may harm the app's assets by exploiting a vulnerability. Test: an action to show the app meets its stakeholders' security requirements. | 4-Web_Application_Security_Testing, `00-Introduction_and_Objectives/README.md`, "What is Web Application Security Testing?", "What is a Vulnerability?", "What is a Threat?", "What is a Test?" |
| The method aims to be consistent, reproducible, rigorous and under quality control, and security testing will never be an exact science with a complete list of issues. The method is black box: the tester knows little or nothing about the app. The model has three parts: the tester, the tools and methodology, and the application. | same file, "The Approach in Writing this Guide" and "What Is the OWASP Testing Methodology?" |
| Passive testing means exploring the app as a user and watching traffic (for example with an HTTP proxy) to list its access points, such as parameters, cookies and APIs. Active testing then uses the guide's methods, in 12 categories: Information Gathering; Configuration and Deployment Management; Identity Management; Authentication; Authorization; Session Management; Input Validation; Error Handling; Cryptography; Business Logic; Client-side; API Testing. | same file, "Passive Testing" and "Active Testing" |

### Reporting (chapter 5)

| What the pages say (my words) | Section or test ID |
|---|---|
| Testing is only half the job. The other half is a well-written report that is easy to understand and speaks to both executives and technical staff. The guide says test quality does not matter if the client cannot understand the findings. | 5-Reporting, `README.md`, opening and "About this Section" |
| The format is suggestions, not strict rules, and fits consultant reports best. It may be too much for internal or bug-bounty reports. The guide advises securing and encrypting the report so only the receiving party can use it. | 5-Reporting, "About this Section" |
| Introduction should hold: version control table, table of contents, team and qualifications, scope, limitations (out-of-bounds areas, broken functionality, lack of cooperation, time, access or credentials), timeline, and a disclaimer. The sample disclaimer says the test is a "point in time" assessment, that not all issues are found, and that it is not a warranty. The guide says to ask a legal professional and not to use the sample as-is. | 5-Reporting, "1. Introduction", 1.1 to 1.7 |
| Executive summary: the test's objective and business need, key findings in business terms (compliance, reputation) without technical details, and strategic recommendations in non-technical words. Avoid jargon and negative speculation. | 5-Reporting, "2. Executive Summary" |
| Findings (for the technical team): a summary table (ID, title, risk level), then details for each: ID, title, likelihood (ease, working exploit code, access needed, attacker motivation), impact, risk (Informational, Low, Medium, High, Critical, with the scale explained in an appendix; CVSS only when needed), a description with sensitive data (passwords, personal data, card numbers) masked, fix steps, and extra resources. Include enough detail to act on. For a re-test, summarize the prior findings and their status. | 5-Reporting, "3. Findings", 3.1 and 3.2 |
| Appendices to add: the methodology used, risk-rating explanations, cleaned tool output (not a raw dump), and a checklist of tests run, such as the WSTG checklist. | 5-Reporting, "Appendices" |

## Limits and cautions

- **Dated.** v4.2 is from December 2020. The foreword text is from 2013, the history appendix says v4.1 was April 2020 and v4.0 was 2014, and v5.0 is in development. Many tool and book links are from 2000 to 2015.
- **Web apps only.** Mobile apps and firmware are sent to other OWASP guides (3.8). It says nothing about cloud services, managed databases, serverless hosting or row-level security in this part. Chapter 4 test pages (not in this file) may cover APIs.
- **Black-box method.** The core method assumes the tester knows little about the app, yet the guide also says source code review is better and the code should be shared.
- **Stale items.** Tool names in Appendix A (for example Samurai, Santoku, ActiveX and `.NET` era references, Firefox Tamper Data, Internet Explorer and "Edge/IE" in Appendix F) and some commercial products may no longer exist or may be renamed. I did not check which. The XSS strings in Appendix D are about browser behavior that was described as "previously" working in IE but not Firefox, so do not treat them as current attacks. The "$2.84 trillion" and "$100,000" figures are old and from other sources, so quote them only as the guide's reported numbers, if at all.
- **Compliance wording.** The guide names HIPAA only in a list of industry rules (3, Phase 3.2) and in an old 2012 slide reference. It does not explain what HIPAA requires. Do not use this source to say the proposed coordinator needs, meets or avoids any law. The guide itself says to talk to legal counsel.
- **Tests do not prove safety.** The guide states that a clean test does not mean the software is good and that the report is a point-in-time view. The paper must not say any design is "secure" or "compliant" based on this source.
- **Authority.** OWASP is a volunteer community project. It is respected and widely used but is guidance, not law or a certification standard.
- **Figures not viewed.** Figures 2-1 to 2-5 and 3-1 are images; I read only their captions.
- **Licence.** CC BY-SA 4.0 (credit OWASP and share alike if material is reused).
