## What the pages say (my words)

| What the pages say (my words) | Test ID and section |
|---|---|
| Reflected XSS: the site takes input from a link or form and sends it straight back in the page without making it safe. A harmful link then runs the attacker's script in a victim's browser. The test finds every input that is echoed back and checks which special characters (such as angle brackets, quotes, ampersand) are not converted to safe HTML codes. The guide warns that deny lists miss variants (different encodings, odd spacing, split words), so it says most protection must come from the application cleaning or encoding input. Browser and firewall protections cannot be assumed. | WSTG-INPV-01, "Summary", "Test Objectives", "Bypass XSS Filters" |
| Stored XSS: harmful input is saved (profile, comment, setting, file upload, log) and runs later when other users, especially admins, view it. The test lists every place input is stored and then displayed, checks how it is placed in the HTML, and tries the same input by GET and POST. It also checks file uploads: uploads that allow HTML content, or let the sender pick the content type, can run script in the browser. The guide calls this the most dangerous XSS type. | WSTG-INPV-02, "Summary", "Input Forms", "File Upload" |
| HTTP Verb Tampering: the page is empty. It says the content was merged into the "Test HTTP Methods" page (a different part of the guide, not read here). | WSTG-INPV-03, whole page |
| HTTP Parameter Pollution: sending the same parameter name twice can make different parts of a system read different values (first, last, or joined). The guide gives a table of how common servers behave and old real cases (a firewall bypass, and a blog-ownership bug where the permission check read one value and the action used the other). The test sends the normal value, a changed value and both together, then compares responses. The guide says this needs manual testing because tools give many false alarms. | WSTG-INPV-04, "Summary", "Expected Behavior by Application Server", "How to Test" |
| SQL injection (general): if user input is joined into a SQL query, an attacker can change what the query does, and read, change or delete data. The guide names in-band, out-of-band and blind (inferred from behavior) kinds, and techniques such as union, boolean, error-based, out-of-band and time delay. It also covers stored procedures that build SQL from text. Detection means finding every input that reaches a database (including headers and cookies) and watching for errors or changed results. Remediation is a pointer only: see OWASP's SQL Injection Prevention and Database Security cheat sheets and the Input Validation cheat sheet. Many pages of attack examples and filter-evasion tricks follow. | WSTG-INPV-05, "Summary", "Detection Techniques", "Exploitation Techniques", "Remediation" |
| Oracle (PL/SQL gateway): a web layer that passes requests to the database. Old gateways let attackers call dangerous database packages, and block lists for those packages were bypassed again and again. The test first checks whether the gateway is present, then tests each input for SQL injection. | WSTG-INPV-05.1, whole page ("Testing for Oracle") |
| MySQL: lists MySQL-specific quirks (how quotes are handled, comment tricks, version checks, file read/write if the database user has the FILE privilege, and that its connectors do not run several statements in one call). Written for MySQL 3.23 to 5.0, so very old. | WSTG-INPV-05.2, whole page ("Testing for MySQL") |
| SQL Server: lists Microsoft SQL Server features an attacker could abuse once injection works (running operating-system commands through an extended procedure, reading the registry, timing tricks, using the database as a port scanner). Tied to SQL Server 2000/2005 behavior. | WSTG-INPV-05.3, whole page ("Testing for SQL Server") |
| PostgreSQL: lists PostgreSQL features that raise the damage of an injection: running several statements, reading and writing server files, and adding functions that call the operating system (including untrusted language add-ons such as PL/Python and PL/Perl). It also shows how to identify PostgreSQL from errors and use sleep for timing. Version examples are 8.x, so old. The page says these features depend on the database user's rights. | WSTG-INPV-05.4, whole page ("Testing PostgreSQL") |
| MS Access: notes that Access lacks comments, stacked queries and LIMIT, and shows workarounds. Also warns that a database file left in a web folder can be downloaded whole. | WSTG-INPV-05.5, whole page ("Testing for MS Access") |
| NoSQL injection: databases that do not use SQL can still be injected through their own query format (such as JSON or JavaScript expressions). Filtering HTML characters does not help against JSON syntax. The impact can be higher because injected code may run as a full programming language. The guide uses MongoDB examples (the `$where` operator) and says each NoSQL product needs its own tests. It also notes that duplicate parameters can create reserved variable names in some languages. | WSTG-INPV-05.6, "Summary", "Testing for NoSQL Injection Vulnerabilities in MongoDB" |
| ORM injection: an object-relational mapping (ORM) library usually gives safe functions, but an app can still be injectable if it builds query text from input, or if the ORM library itself has a bug. The guide gives a Java example of unsafe string joining versus a placeholder, and names past ORM and query-builder bugs (Sequelize and Laravel in 2019, Hibernate research in 2020). The test: identify the ORM, then look for unsafe use and known library flaws. | WSTG-INPV-05.7, "Summary", "Weak ORM Implementation", "Vulnerable ORM Layer" |
| Client-side SQL injection: browser pages using the old Web SQL database feature can be injected if they join untrusted input (like a URL fragment) into queries. Remediation is the same as for server-side SQL injection. | WSTG-INPV-05.8, "Summary", "Web SQL DB Injection", "Remediation" |
| LDAP injection: if input is put into a directory (LDAP) search filter, an attacker can widen the search, read other users' data, or bypass a login. The test tries special filter characters and checks for errors or extra results. Remediation is only a pointer to the LDAP Injection Prevention cheat sheet. | WSTG-INPV-06, "Summary", "How to Test" |
| XML injection: input placed into an XML document can break its structure, add extra tags (for example to raise someone's privilege), or turn on external entities (XXE) that make the parser read files or contact other systems. The test sends XML special characters and watches for parse errors. The source-code section lists parser classes to check and says to forbid DTDs and external entities (pointer to the XXE Prevention cheat sheet). | WSTG-INPV-07, "Summary", "Discovery", "Tag Injection", "Source Code Review" |
| SSI injection: on servers that process "server-side include" directives, injected directives can print files or run commands. The test first checks whether the server supports SSI (for example `.shtml` pages), then injects directives through inputs and headers. The guide notes the command-running directive is usually off by default. | WSTG-INPV-08, "Summary", "How to Test" |
| XPath injection: like SQL injection but against XML data queried with XPath. It can bypass logins or read data, and the guide says there is no access control inside the XML document. Test by adding a single quote and watching for errors. | WSTG-INPV-09, "Summary", "How to Test" |
| IMAP/SMTP injection: in webmail-style apps, input that goes to mail servers can carry extra mail commands, which may reach servers not meant to be public. The test changes mail-related parameters (empty, random, special characters, removed) and classifies the response. | WSTG-INPV-10, "Summary", "Identifying Vulnerable Parameters", "IMAP/SMTP Command Injection" |
| Code injection: input is treated as code or as a file to include, and runs on the server. The page is short, with a PHP example (a URL passed to an include) and an ASP example (user input saved to a file and then executed). It says proper input validation and secure coding are needed but gives little detail. | WSTG-INPV-11, "Summary", "How to Test" |
| Local file inclusion (LFI): when a page takes a file name from the user and includes it, an attacker can read other files on the server using path tricks, and in some PHP setups run code. Remediation: avoid passing user input to file functions; if you must, keep an allow list of files and use an ID to pick one, and reject anything else. | WSTG-INPV-11.1, "Summary", "How to Test", "Remediation" |
| Remote file inclusion (RFI): the same idea, but the attacker supplies a web address, so the server loads and runs a remote file. Same remediation (allow list and IDs). | WSTG-INPV-11.2, "How to Test", "Remediation" |
| Command injection: input that reaches an operating-system command can add extra commands. The test appends command separators to inputs (file names, folder names). The page lists risky functions in Java, C/C++, Python and PHP. Remediation: allow-list the allowed characters or commands (deny lists miss things), and run the app with permissions that do not allow command execution. | WSTG-INPV-12, "Summary", "Special Characters for Comand Injection", "Code Review Dangerous API", "Remediation" |
| Buffer overflow: the page says "This content has been removed" (no test content). | WSTG-INPV-13 (first file), whole page |
| Format string injection: if user input is used as the format text of a print-style function, an attacker can crash the program or leak memory. It is worst in C/C++ and Perl, less severe in Python, Java and PHP. The test uses static analysis, manual code review, and sending conversion codes as input (or fuzzing). The fix shown is to pass user input as an argument, never as the format. | WSTG-INPV-13 (second file), "Summary", "How to Test" |
| Incubated (stored, delayed) vulnerability: an attacker plants data that is saved and later "recalled" by another user or system, using weak input checks or a back door such as an admin console or batch job. Examples: stored XSS in forums, uploaded harmful files, SQL injection that changes page content. Gray-box advice: check input validation on every system that writes to the same data store, and also encode output before showing it. | WSTG-INPV-14, "Summary", "Gray-Box Testing" |
| HTTP splitting and smuggling: splitting means input containing line-break characters ends up in a response header and creates a second fake response, which can poison a cache. Smuggling means different servers and firewalls read the same message differently (for example, two length headers), which can hide attacks from a firewall. The page says smuggling does not exploit the application itself, and relies on a 2005 example against IIS 5.0. | WSTG-INPV-15, "Summary", "HTTP Splitting", "HTTP Smuggling" |
| HTTP incoming requests: how to watch all requests going into a web server without changing the browser, using a reverse proxy, port forwarding, or packet capture, to spot suspicious or unnecessary requests. This is a monitoring technique, not an injection test. Names Fiddler, Charles, Wireshark and others. | WSTG-INPV-16, "Summary", "How to Test" |
| Host header injection: if the app trusts the Host header (or X-Forwarded-Host), an attacker may cause redirects, poison a cache, or make password-reset links point to the attacker's site so the reset token leaks. The test sends another domain in those headers and checks what the app does with it. No remediation section. | WSTG-INPV-17, "Summary", "X-Forwarded Host Header Bypass", "Password Reset Poisoning" |
| Server-side template injection (SSTI): if user input is placed inside a server-side template (Jinja2, Twig and similar), the server may run attacker code. The test sends template expressions (for example a small math expression) and sees if the server evaluates them, then identifies the engine. The guide gives exploit-building steps but no remediation section. | WSTG-INPV-18, "Summary", "Identify Template Injection Vulnerability", "Identify the Templating Engine" |
| Server-side request forgery (SSRF): the app can be tricked to fetch a URL or file for the attacker, reaching internal services or files that users cannot reach directly (including through PDF generators and blind cases where nothing is shown). Common bypass tricks for localhost blocks are listed. The guide says SSRF is among the hardest attacks to defeat without allow lists of permitted addresses, and points to the SSRF Prevention cheat sheet. | WSTG-INPV-19, "Summary", "How to Test", "Remediation" |
| The section index lists the 19 tests with sub-tests for SQL injection (Oracle, MySQL, SQL Server, PostgreSQL, MS Access, NoSQL, ORM, client-side) and for code injection (LFI, RFI). | README.md ("4.7 Input Validation Testing") |

## Useful for the paper

Topic numbers: 1 intro to the field, 2 career relevance, 3 what the field covers, 4 current methods/tools, 5 risks/challenges, 6 trends, 7 best practices, 8 application to the proposed caregiving coordinator.

- **Topic 3 (what the field covers):** this section is a good list of what "input validation testing" covers in web application security testing: 19 test areas, from script injection to database injection to server request tricks. The shared idea is that untrusted input is treated as code or commands somewhere. This is the strongest use of the file.
- **Topic 4 (methods/tools):** the guide's method is black-box (no source), gray-box (some knowledge) and code review. Tools named include proxies (Burp, OWASP ZAP), sqlmap, wfuzz, and static analyzers. Many of the tools named are old (see Limits).
- **Topic 5 (risks/challenges):** the pages repeatedly say deny lists fail, filters can be bypassed, and some flaws (smuggling, parameter pollution, SSRF) are hard to test because they depend on how several components behave together. Stored XSS and incubated attacks matter most where many users view the same data, such as a shared care record.
- **Topic 7 (best practices):** the remediation ideas the guide actually states are few: use allow lists instead of deny lists (command injection, file inclusion, SSRF), use placeholders for ORM queries (WSTG-INPV-05.7), encode output as well as validate input (INPV-14), run the app with least permissions (INPV-12), forbid external entities in XML parsers (INPV-07), and use OWASP cheat sheets for SQL injection, LDAP and SSRF. For anything more detailed the paper should cite the cheat sheets themselves, not this guide.
- **Topic 8 (the proposed coordinator, Next.js + Supabase + Vercel; a product idea, not built):**
  - *Most relevant tests:* WSTG-INPV-01 and -02 (reflected and stored XSS): shared notes, care-task text, comments and profile names will be saved and shown to other family members; React escapes text by default, but the guide's point is to test every place that shows stored text and any use of raw HTML. WSTG-INPV-05 (SQL injection), -05.7 (ORM) and -05.6 (NoSQL idea, JSON-style queries): Supabase uses a client library and an API layer over Postgres rather than hand-built SQL, so the practical questions are whether any code builds queries from text and whether the library has known bugs; the ORM page's "a library can itself be vulnerable" point applies, though it does not name Supabase. WSTG-INPV-14 (incubated): data saved by one family member and viewed by another is the exact pattern. WSTG-INPV-04 (parameter pollution): API routes that read query or form values. WSTG-INPV-17 (Host header and password-reset poisoning): relevant if the product sends reset or invite links by email; the guide's point is not to build those links from the incoming Host header. WSTG-INPV-19 (SSRF): relevant if the product ever fetches a URL a user provides (for example link previews, document import or webhooks). WSTG-INPV-02 file-upload section: relevant if caregivers upload photos or documents (for example prescription images).
  - *Low relevance and why:* Oracle, MySQL, SQL Server and MS Access pages (the planned database is Postgres, and those pages describe old products); PostgreSQL page (the right database, but its examples assume the attacker can run arbitrary statements and add server-side functions, which a hosted managed Postgres may restrict; this is my inference and was not checked against Supabase documentation); LDAP, XPath, IMAP/SMTP, SSI (the planned stack has no directory service, XML database, webmail or SSI); LFI and RFI and code injection pages (the examples are PHP and ASP include patterns, not Next.js); buffer overflow and format string (C/Java-style issues; the buffer overflow page is empty); client-side Web SQL (a deprecated browser feature); HTTP smuggling and incoming-requests monitoring (mostly infrastructure the hosting provider controls). Command injection (INPV-12) and SSTI (INPV-18) matter only if the app ever runs system commands or renders user text as a template, which is not in the planned design; I would list them as "check and rule out" rather than main risks.
  - The guide says nothing about Supabase, Next.js, Vercel, row-level access rules, or health data. Any link to those must come from other sources.

## Limits and cautions

- **Dated:** v4.2 is from December 2020. The section's tools and examples are often much older (examples assume MySQL 3.23 to 5.0, SQL Server 2000/2005, IIS 5.0, PHP and ASP sites, Flash, Internet Explorer, Web SQL). Tools named (for example Fiddler classic, ratproxy, XSS-Proxy, sqlbftools, MySqloit, BeEF) may be unmaintained or changed; I did not check each tool's current status. v5.0 is in development, so newer guidance may exist.
- **Tester-focused:** the pages are written for people attacking a site to test it, so they show attack steps. I put only one-line descriptions in these notes and did not copy any attack strings. Remediation is shallow in most pages; several (SSTI, host header, buffer overflow, verb tampering) have none or are empty stubs.
- **Not tied to modern stacks:** no page covers JavaScript frameworks, serverless hosting, or managed databases with API layers. The paper should say that applying these tests to the proposed coordinator is my inference, not something the guide states.
- **Safety wording:** passing these tests would not show a product is "secure". The guide itself says some tests need manual work and that tools give false alarms (INPV-04).
- **Quote (under 15 words):** the SSRF page says SSRF "is known to be one of the hardest attacks to defeat" without allow lists (WSTG-INPV-19, "Remediation"). I paraphrased it above; no other quotes are used.
