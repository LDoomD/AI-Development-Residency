## What the pages say (my words)

| Point | Where |
|---|---|
| CVSS is an open framework for communicating the characteristics and severity of software vulnerabilities. It has four metric groups: Base, Threat, Environmental, Supplemental. Scores run from 0 to 10. | Specification, opening paragraph and Introduction |
| Base metrics are the intrinsic qualities that do not change over time or across environments. Threat metrics change over time. Environmental metrics are specific to one user's environment. Supplemental metrics add context and **never change the score**. | Specification, Introduction and Metrics |
| Base metrics (and Supplemental) come from the vendor or a third party for it. Threat and Environmental information is known only to the end consumer, who should add it. | Specification, Introduction |
| CVSS says it cannot weigh regulations, number of customers affected, money lost, risk to life or property, or reputation. Those are outside CVSS. | Specification, Introduction |
| A **Base score measures severity, not risk**. The User guide says the Base score "should not be used alone to assess risk." A score that uses Threat and Environmental data (CVSS-BTE) is "much closer to risk". | User guide, "CVSS Base Score (CVSS-B) Measures Severity, not Risk" |
| Scores must be labeled by which metrics were used: CVSS-B (base only), CVSS-BT, CVSS-BE, CVSS-BTE. Providers such as vendors and the National Vulnerability Database typically publish only CVSS-B. | Specification, Nomenclature |
| Base metrics: Attack Vector (Network, Adjacent, Local, Physical), Attack Complexity (Low, High), Attack Requirements (None, Present; new in 4.0), Privileges Required (None, Low, High), User Interaction (None, Passive, Active). Impact is scored for the vulnerable system and separately for any "subsequent system" on confidentiality, integrity and availability. | Specification, Base Metrics |
| Attack Vector is higher the more remote the attacker can be. Attack Complexity covers built-in defenses the attacker must evade. Attack Requirements covers conditions that arise from how the system is deployed (for example a race condition or an on-path attacker). | Specification, Base Metrics; FAQ, "What’s the difference between Attack Complexity (AC) and Attack Requirements (AT)?" |
| Self-service accounts do not count as a privilege requirement if the attacker can grant themselves the privilege. Default or hard-coded credentials count as Privileges Required: None. | Specification, Privileges Required |
| Integrity includes non-repudiation: if a system user can deny a critical action because logging is missing, that is an integrity impact (the User guide cites CWE-778, insufficient logging). | Specification, Integrity; User guide, "Non-Repudiation is a Part of Integrity" |
| Confidentiality and integrity are about the data; availability is about the service. A bug that lets an attacker alter web files affects integrity, not availability, if the service still runs. | User guide, "Confidentiality and Integrity, Versus Availability Impacts" |
| Threat metric: Exploit Maturity (Not Defined, Attacked, Proof-of-Concept, Unreported). The default, Not Defined, counts as the worst case (Attacked). Threat data can only lower the score. The consumer must fill it in, preferably from several threat-intelligence sources, automatically and often (the FAQ suggests daily updates). | Specification, Threat Metrics; FAQ |
| Environmental metrics: Confidentiality, Integrity and Availability Requirements (Low, Medium, High; default counts as High) and "Modified" versions of every Base metric. The User guide gives rules of thumb, for example: a system with PII or money data rates High for integrity, and a system that stores unencrypted login credentials rates High for confidentiality. Data used to make health decisions rates High for integrity. | Specification, Environmental Metrics; User guide, "Security Requirements" |
| "Safety" is both a Modified metric (for the consumer) and a Supplemental metric (for the vendor). It uses IEC 61508 injury categories (negligible, marginal, critical, catastrophic). A missing Safety value does not mean there is no safety impact. | Specification, Modified Base Metrics and Safety; Supplemental Metrics |
| Supplemental metrics: Safety, Automatable, Recovery, Value Density, Vulnerability Response Effort, Provider Urgency. The consumer decides how to use them. The FAQ says if an exploit can be automated, consider fixing sooner, "as soon as there is a public proof of concept". | Specification, Supplemental Metrics; FAQ |
| Severity rating scale: None 0.0; Low 0.1 to 3.9; Medium 4.0 to 6.9; High 7.0 to 8.9; Critical 9.0 to 10.0. Using the words is optional. | Specification, Qualitative Severity Rating Scale |
| The vector string starts with "CVSS:4.0/" and lists metrics in a fixed order. All Base metrics are mandatory. | Specification, Vector String |
| How the numbers are made: about 15 million possible vectors were grouped into 270 sets; experts compared the sets, a chess-style Elo ranking ordered them, and a lookup table plus interpolation gives the score. The scoring lookup is in the calculator code on GitHub. | Specification, "CVSS v4.0 Scoring"; User guide, "New Scoring System Development" |
| Changes from 3.1: "Scope" is replaced by vulnerable and subsequent systems; Attack Requirements is new; User Interaction now has Passive and Active; "Temporal" is renamed "Threat"; Supplemental metrics and an extension framework were added; the vector begins with "CVSS:4.0". | User guide, "Changes in CVSS Version 4.0" |
| Advice to consumers: join scan results with asset data (to use Environmental metrics) and with threat intelligence (to use Exploit Maturity), using automation. | User guide, Assessment Guide |
| Vulnerability chaining: score each part and the combined chain; list generic classes of related weaknesses rather than giving attackers new ideas. | User guide, "Vulnerability Chaining" |
| Libraries: the maintainer scores the reasonable worst case; each product that uses the library must re-assess for its own use, and may find the score is 0 if the vulnerable function is not reachable. Only consumers apply Threat and Environmental metrics. | User guide, "Assessing Vulnerabilities in Software Libraries"; FAQ, "What are best practices for vulnerability assessments that differ depending on the platform?" |
| Reflected XSS: user interaction is Active (a person chooses to click a link). Stored XSS: Passive. In XSS the web application is the vulnerable system and the user's browser is a subsequent system. | FAQ; Examples (reflected and stored XSS) |
| One vulnerability can have several valid scores (different products) or wrong ones (errors); consumers must check the source of each. CVSS does not require a CVE ID. | FAQ |
| CVSS, EPSS and SSVC are not replacements for each other. EPSS estimates the chance of exploitation in 30 days; SSVC is a decision tree. | FAQ, "Is EPSS or SSVC a replacement for CVSS?" |
| For AI and LLM issues, CVSS fits only measurable confidentiality, integrity or availability impacts; it is "not" for ethical or legal problems. | FAQ, "How can I apply CVSS concepts to AI / LLM application issues?" |
| The FAQ says a CISA directive named "BOD 26-04: Prioritizing Security Updates Based on Risk" is a rubric for patch priority and that CVSS Base scores "should not be used alone". I did not read that directive, so treat it as FIRST's statement only. | FAQ, "How does CVSS provide input to patch priority?" |
| The FAQ warns that the default Threat value (Attacked) and default Requirements (High) can push a vendor score toward an unrealistic worst case, and that different vulnerabilities can share the same number. | FAQ, "How does CVSS calculate numeric scores from vector strings?" |
| The Examples page scores about 40 real vulnerabilities with comments per metric. Examples that fit a small web product: stored and reflected XSS, CSRF (CVE-2023-5602, Base 5.1), SQL injection (CVE-2023-30545, Base 7.1), SSRF (CVE-2024-1233), authentication token flaw (CVE-2023-48228), information disclosure, privilege escalation, and the log4j library flaw (CVE-2021-44228, Base+Threat 9.3, with a variation for immutable containers that lowers it to 5.5). | Examples |
| Examples show that the same flaw can score very differently once the consumer adds context (for example CVE-2026-31431 drops to 0.0 when a documented mitigation is in place; CVE-2023-20048 drops from 6.4 to 2.4). | Examples, Linux Kernel; Management System |
| The Examples page includes a "CISA KEV Examples" section: CVE-2026-96656 (Plex Media Server), Base+Threat 8.6, Exploit Maturity Attacked because "CISA has reported attempts to exploit this vulnerability". | Examples, "CISA KEV Examples" |

## Possible use in the paper
- **Topic 5 (what it includes) and topic 6 (what teams do):** CVSS is the common way a team ranks vulnerabilities. The strongest, plainest points: a Base score is severity and not risk; the consumer adds threat and environment; and scores must be shown with their vector string and label (CVSS-B, BT, BE or BTE).
- **Topic 7 (tools and skills):** reading and adjusting a CVSS vector is a basic skill. Pair this with the CISA Known Exploited Vulnerabilities list (the page's own "Threat Intelligence" glossary names CISA KEV).
- **Topic 8:** a plan for the proposed coordinator can say that when a dependency alert appears (npm audit, the host's alerts), the owner would not rank it by the Base score alone, but would check whether it is on the CISA list and whether the affected code is reachable. The paper must label this as a plan.

## Limits
- CVSS scores technical severity only. It does not cover privacy harm, legal exposure or harm to a care circle. Do not describe a CVSS score as "risk" (the User guide says not to).
- Some Examples pages show a heading score that disagrees with the table. I saw two: the CVE-2023-48228 heading says Base 9.4 while its table row says 9.3, and the Linux kernel example heading says "Base 10.0" while its v4.0 Base row is 8.5. If the paper quotes an Examples score, quote the table row and recheck against the vector.
- Several Examples (CVE-2026-xx) have dates and details I cannot verify from outside the page.
- I did not run the calculator or recompute any score. I did not read the CVSS Implementation Guide or the GitHub calculator.
