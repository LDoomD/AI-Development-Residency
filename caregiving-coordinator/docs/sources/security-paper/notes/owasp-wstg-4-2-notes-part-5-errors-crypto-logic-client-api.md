## What the pages say (my words)

| What the pages say (my words) | Test ID and section |
|---|---|
| **Improper error handling.** Apps, web servers and databases all produce errors, and developers often only plan for the "happy path." Errors can show stack traces, memory dumps, timeouts and input mismatches. Attackers can learn which tools and versions run inside, map how services connect (especially in microservice setups), crash the system, or bypass controls. Goal: find the error output and study it. Checks: ask for pages that do not exist (404), ask for real folders (403 or listing), and break the HTTP rules (huge path, bad headers, wrong version) so the web server shows itself. For apps, find every input, learn its type, then fuzz it (or hand-pick inputs likely to break a parser, such as a missing JSON bracket). Watch for errors hidden as "success" replies or redirects. Fix: see OWASP Proactive Controls C10 and the Error Handling Cheat Sheet (the page gives no steps of its own). | WSTG-ERRH-01, Summary, How to Test (Web Servers, Applications), Remediation |
| **Stack traces.** This page only says it was merged into WSTG-ERRH-01. | WSTG-ERRH-02 |
| **Weak transport layer security (TLS).** Data moving between browser and server must be encrypted (usually HTTPS/TLS), and the server must prove who it is with a trusted certificate. Old protocol versions and ciphers have known flaws (SSLv2, SSLv3, TLS 1.0, export, NULL, anonymous and RC4 ciphers, CBC mode, TLS compression, weak key exchange). The page says these lab attacks are "not generally considered practical" in the real world, since they need an active man-in-the-middle and many resources. Certificate checks: key at least 2048 bits, signature at least SHA-256 (not MD5 or SHA-1), still valid, lifespan no more than 398 days for certificates issued after 1 Sept 2020, signed by a trusted authority, name matches the host. Wildcard certificates have trade-offs. App-level checks: no mixed active content (scripts or CSS loaded over plain HTTP on an HTTPS page), HTTP-to-HTTPS redirects plus the HSTS header, and the HSTS preload list. Tools named: Nmap, O-Saft, sslscan, sslyze, SSL Labs, testssl.sh, `openssl s_client`. Fix: follow the Mozilla Server Side TLS guide. | WSTG-CRYP-01, Server Configuration, Digital Certificates, Implementation Vulnerabilities, Application Vulnerabilities, Automated Testing |
| **Padding oracle.** If an app decrypts data sent by the browser (for example session state kept on the client) and leaks whether the padding was valid, an attacker can read the data and forge new data without the key. Leaks can be error messages, small reply differences or timing. Test: find random-looking values whose length fits block sizes (8 or 16 bytes), flip bits, and compare three outcomes (good, garbled, padding error). Gray-box: confirm the ciphertext is checked for integrity (HMAC, or GCM/CCM modes) and that all decryption errors look the same. A safe design gives only "ok" or "failed." Tools named (PadBuster, POET, Bletchley and others) are old. | WSTG-CRYP-02, Summary, Black-Box Testing, Gray-Box Testing, Tools |
| **Sensitive data on unencrypted channels.** If data must be protected when stored, it must also be protected in transit. Examples: logins, session cookies, and personal data such as healthcare and medical insurance information (the page lists both). Checks: Basic authentication over HTTP, login forms that post to `http://`, session cookies without the Secure flag, and searching source code and logs for hard-coded passwords, keys or personal data (with grep). Tools: curl, grep, Wireshark, tcpdump. | WSTG-CRYP-03, Summary, How to Test (Examples 1 to 4) |
| **Weak encryption.** Bad algorithm or parameter choices lead to data exposure, key leaks and broken sessions. Checklist (as of 2020): random, unpredictable IVs; ECC (Curve25519 preferred) or RSA of 2048 bits or more; avoid MD5, RC4, DES, Blowfish and SHA-1; no ECB mode; for password hashing use PBKDF2, scrypt or bcrypt (PBKDF2 over 10,000 iterations, random salt). Source code review: search for weak-algorithm names and hard-coded secrets. Examples are in Java. Fix: see the Cryptographic Storage and Password Storage cheat sheets. Some details are dated (the 10,000 iteration advice, and the CBC and SSH line is unclear). | WSTG-CRYP-04, Basic Security Checklist, Source Code Review, Tools |
| **Intro to business logic.** Logic flaws come from using a feature in a way the designers did not plan (for example jumping from step 1 to step 3). Scanners cannot find them; the page says automation of business logic abuse cases is "not possible." A person must know the business rules and think up misuse cases. Proxy tools (ZAP, Burp) only help to see and change requests. | Business Logic Testing, 4.10.0 Introduction |
| **Business logic data validation.** Checking data in the browser is not enough; the server and every hand-off between systems must check that data is logically valid, not only well formed. Examples: sending an in-stock order as out-of-stock to a partner, decisions based on stale nightly data, and a "denial of dollars" campaign that used a bank's free-transfer limit. Test: find data entry and hand-off points, then send logically invalid values through a proxy. Fix: accept only logically valid data at every input and hand-off, and never trust data just because it is inside the system. | WSTG-BUSL-01, Summary, How to Test, Remediation |
| **Forging requests.** Attackers skip the screen and send requests directly, using guessable values, hidden fields or hidden developer features (debug switches). Example: a hidden "discount taken" field set back to "no" to reuse a one-time discount. Test: watch for values that count up or are easy to guess, and for hidden options. Fix: design the logic so parameters cannot be predicted or changed to skip steps, and remove undocumented features. | WSTG-BUSL-02, Summary, How to Test, Remediation |
| **Integrity checks.** Hidden fields, drop-downs and read-only controls are only locked inside the browser; a proxy can change them. The server must keep its own copy of values and check them against the user's rights (for example a non-admin sending an admin-only "change password" request, or submitting a project name they were not offered). Logs must also be protected from reading, editing and deleting. Test: change hidden and read-only fields, and try to read or edit components such as logs and databases. Fix: strict access control on data and logs, trusted channels, and logging to catch tampering. | WSTG-BUSL-03, Summary, Specific Testing Methods 1 to 3, Remediation |
| **Process timing.** Response time can leak information (for example a login that takes longer for a real username), and open sessions or held items (reserved seats, price quotes) can be abused by waiting. Test: list time-dependent steps, automate the requests, and compare. Fix: make results take the same time where timing would help an attacker, and cancel or reset transactions after a set time. | WSTG-BUSL-04, Summary, How to Test, Remediation |
| **Limits on how often a function can be used.** If an action should happen once or a set number of times (a discount, a monthly download limit), attackers may go back and repeat it. Test: find such functions and try repeating them (back button, reloading carts). Fix: hard limits enforced on the back end or in the database, per user, not in the screen. | WSTG-BUSL-05, Summary, How to Test, Remediation |
| **Circumventing work flows.** Steps must happen in the right order, and if a flow is cancelled, everything it started must be rolled back (for example loyalty points kept after a cancelled sale, or a post edited after the profanity check was passed). Test: skip, reorder or cancel steps and check the results. Fix: the app must check step order and reject skipped or repeated steps. | WSTG-BUSL-06, Summary, Testing Methods 1 and 2, Remediation |
| **Defenses against application misuse.** The test asks whether the app notices and reacts to abuse (changed parameters, blocked file IDs, a burst of failed requests). Example reactions: disable features, add extra sign-in steps, slow requests, record more detail. Localized defenses (reject certain characters, lock an account after failed logins) are not enough. The page lists signals worth watching, including very fast use, a change of country or browser, steps done in the wrong order, and high rates of uploads, downloads, vouchers or failed payments. It says "very few applications" detect these misuses. Fix: add active defenses (the OWASP AppSensor project is cited). | WSTG-BUSL-07, Summary, How to Test, Remediation |
| **Upload of unexpected file types.** The app should accept only file types its business process expects. Risks: executable or script files, or a wrong format that corrupts saved data. Checks: try files that are not approved (jsp, exe, HTML with script); see whether only client-side JavaScript, only the `Content-Type` header, or only the extension is checked; see whether uploaded files can be fetched directly by URL; check for code in the file; and check for zip files that unpack to unintended paths. Fix: allow lists or deny lists of extensions, `Content-Type` checks, or a file type recognizer, so only expected types get in. | WSTG-BUSL-08, Summary, Specific Testing Method, Remediation |
| **Upload of malicious files.** Extension lists alone do not stop a legal file type with harmful contents. Test items: web shells (a script that runs commands, needs a server that runs uploaded code in the web folder); filter evasion (change `Content-Type`, odd or mixed-case extensions, trailing characters or null bytes, a bad nginx setup); malware (the harmless EICAR test file shows whether scanning exists); archive path traversal in zip files; zip bombs (can cause denial of service and higher cloud costs, so do not test without written approval); XML attacks (XXE, billion laughs); and risks in CSV (injection), Office (macros) and PDF (JavaScript) files. The page says full protection is complex and varies by file type; see the File Upload Cheat Sheet. | WSTG-BUSL-09, Malicious File Types, Malicious File Contents, Remediation |
| **DOM-based XSS.** Cross-site scripting that happens only in the browser: page JavaScript takes input from a "source" (for example the URL fragment after `#`) and puts it in a "sink" (for example `document.write`), so attacker code runs. The server may never see it. Automated tools find little of this, so manual code review is needed. Consequences match other XSS (cookie theft, more injected script). Fix: see the DOM-based XSS Prevention Cheat Sheet. | WSTG-CLNT-01, Summary, How to Test, Remediation |
| **JavaScript execution.** A kind of XSS where user input reaches code that runs it (for example `eval` or a redirect to a `javascript:` address). Test: find the sources and sinks. The page's example reads the URL hash and passes it to `eval`. | WSTG-CLNT-02, Summary, How to Test |
| **HTML injection.** If user input is placed on the page without cleaning and output encoding (for example with `innerHTML` or `document.write`), an attacker can insert HTML such as an image tag with an error handler that runs script. Test: find the injection points and judge how serious the injected content can be. | WSTG-CLNT-03, Summary, How to Test |
| **Client-side URL redirect (open redirect).** If the app sends the browser to a URL taken from the page address without checking, attackers can send victims to fake sites (phishing) that look trusted because the link starts with the real site. It can also be used to reach functions that access checks would normally block, or to run `javascript:` code. Test: find code that handles URLs or paths and see where it can redirect. | WSTG-CLNT-04, Summary, How to Test |
| **CSS injection.** If user input reaches style rules, attackers may run script in some conditions (mostly old browsers) or leak values (for example a CSRF token, guessed one character at a time using CSS selectors that make requests). Letting users supply custom CSS is called "a considerable risk." Test: review code that builds CSS from input. Fix: see the Securing Cascading Style Sheets Cheat Sheet. Some payloads are for old IE and Opera. | WSTG-CLNT-05, Summary, How to Test |
| **Client-side resource manipulation.** If input controls the address of a resource the page loads (script, iframe, image, object, AJAX request), attackers can load their own content, often leading to XSS. The page gives a table of risky sinks (iframe src, a href, XHR URL, link href, img src, object data, script src). Test: find inputs that set those values without checks. | WSTG-CLNT-06, Summary, How to Test (sink table) |
| **Cross origin resource sharing (CORS).** CORS lets a server say which other sites' scripts may read its responses, using headers such as Access-Control-Allow-Origin. Risky settings: the `*` wildcard (only fine for a public API intended for everyone) and a server that simply echoes back whatever Origin it receives. The Origin header can be faked outside a browser, so it must not be the only access control. Also check that URLs passed to XHR are validated and that returned data is escaped. Tools: ZAP and manual code review. | WSTG-CLNT-07, Summary (Origin and Access-Control-Allow-Origin, Input Validation), How to Test |
| **Cross site flashing (Adobe Flash).** Covers attacks on Flash (SWF) files: loading outside movies, variables passed in from the page (FlashVars), unsafe ActionScript methods, open redirects, and the `asfunction` and `ExternalInterface` features. Test: decompile the SWF and look for unsafe use of those inputs. Flash is a retired plug-in technology, so this page matters little today. | WSTG-CLNT-08, whole page |
| **Clickjacking.** An attacker puts the target site in a hidden frame (iframe) on a harmless-looking page, so the victim's clicks hit the hidden page while they are signed in. It can get around anti-CSRF tokens because the real page makes the request. Test: try to load the target page in an iframe on your own test page. If it loads, there is no framing protection. Defenses covered: client-side "frame busting" scripts (easy to bypass, with many tricks listed, mostly for old browsers such as IE7/8 and Safari 4), and the server header X-Frame-Options (recommended value DENY; weak spots are old browsers, proxies that strip the header, and mobile or other site versions missing it). A step-by-step bank transfer demo shows the attack. The page does not mention the newer Content-Security-Policy `frame-ancestors` option. | WSTG-CLNT-09, Summary, How to Test, Bypass Clickjacking Protection, Server-side Protection, Create a Proof of Concept |
| **WebSockets.** WebSockets give a two-way channel after an HTTP handshake. Check that the server verifies the Origin header on the handshake (or other sites may connect, a CSRF-like problem), that `wss://` (encrypted) is used instead of `ws://`, and test sign-in, permissions and input cleaning the same way as for normal HTTP, because WebSockets do not handle authentication or authorization. Tool: ZAP WebSocket tab. | WSTG-CLNT-10, Summary (Origin, Confidentiality and Integrity, Input Sanitization), How to Test |
| **Web messaging (`postMessage`).** Pages in different origins may swap messages. Senders must name the exact receiving origin and not use `*`. Receivers must check `event.origin` exactly (a check like "contains .owasp.org" can be fooled by `www.owasp.org.attacker.com`) and still treat message data as untrusted (do not use `eval` or `innerHTML`; `innerText` is safer). | WSTG-CLNT-11, Examine Origin Security, Examine Input Validation, Static Code Analysis |
| **Browser storage.** Local storage, session storage, IndexedDB, cookies and the global window object can all be read and edited with browser developer tools. Goal: see whether sensitive data is kept in the browser and whether storage handling code can be injected into. Check that any stored crypto keys are not marked extractable when they should not be. Fix, in one line: keep sensitive data on the server, stored in a protected way. | WSTG-CLNT-12, Test Objectives, How to Test, Remediation |
| **Cross site script inclusion (XSSI).** A page on another site can include your script files (the same-origin rule does not apply to `<script>` tags). If those files hold private data for a signed-in user (API keys, personal data), the attacker's page can steal it through global variables, function arguments, CSV or JSON tricks, runtime errors (old IE) or prototype tricks. Test: compare signed-in and signed-out responses to spot dynamic script files, and check which could leak. The page gives no remediation section. | WSTG-CLNT-13, Summary, How to Test (items 1 to 5) |
| **GraphQL testing.** Goals: a production-ready setup, input checks on every field, and proper access control. Checks: introspection queries (let anyone read the whole schema, so limit them); the GraphiQL and Playground tools (should not be reachable in production); authorization (GraphQL does not enforce permissions by default, the app must; the demo exposes tokens to any user); injection (SQL, XSS and others still work, only the entry point changes); denial of service from deeply nested queries; batching attacks (many queries in one request can slip past rate limiters and speed up guessing); detailed error messages; and a GraphQL layer that forwards to an older API without checking authorization. Fix list: limit introspection, validate input, set timeouts and maximum query depth and complexity, throttle by server time, give generic errors, and limit batching and per-object request rates. Tools: GraphQL Playground, Voyager, sqlmap, InQL, GraphQL Raider, ZAP add-on. | WSTG-APIT-01, Test Objectives, How to Test (Introspection, Authorization, Injection, DoS, Batching, Detailed Error Message, Exposure of Underlying API), Remediation |

## Useful for the paper

| Paper topic | What these pages give |
|---|---|
| 1. Intro to the field | The WSTG is a community testing guide. These chapters show application security testing is a mix of tool-based checks (TLS scans, header checks) and human thinking (business logic). |
| 2. Career relevance | The business logic intro says logic flaws need tester skill and knowledge of the business, and tools cannot find them (WSTG 4.10.0). That is a human-skill point for a career section. |
| 3. What the field covers | Chapters 4.8 to 4.12: error handling, weak cryptography, business logic (including file upload), client-side attacks, and API (GraphQL) testing. |
| 4. Current methods and tools | Intercepting proxies (ZAP, Burp), TLS scanners (SSL Labs, testssl.sh, sslyze), fuzzing, manual code review, and GraphQL tools (Playground, Voyager, InQL). The padding oracle and Flash tool lists are old. |
| 5. Risks and challenges | Logic flaws cannot be automated; DOM XSS is missed by many scanners; the TLS page says many lab attacks are impractical; the misuse-defense page says few applications detect abuse. |
| 6. Trends | GraphQL appears as a newer API style with its own attack surface. The guide's age (2020) is itself a limit for trends (no mention of newer browser protections such as `frame-ancestors` in the clickjacking page). |
| 7. Best practices | Generic error messages; server-side checks of every value and hand-off; hard limits enforced in the back end or database; strict check of step order; HSTS and valid certificates; keep sensitive data on the server, not in browser storage; exact origin checks for CORS and `postMessage`; GraphQL query depth, complexity and batching limits. |
| 8. Application to the proposed caregiving coordinator | See below. |

**Flags for topic 8 (the proposed Next.js, Supabase, Vercel coordinator; a product idea, not built):**

- **File upload (WSTG-BUSL-08 and 09):** if caregivers could upload documents or photos, the proposed coordinator would need an allow list of file types, content checks (not just extension or `Content-Type`), scanning, and care with archives and PDFs. The guide's examples are PHP and web shells on a classic web server, so the paper should say these map loosely to a hosted storage setup and needs its own review.
- **Rate limits and function-use limits (WSTG-BUSL-05, BUSL-07):** relevant to sign-in attempts, invites, and any "send reminder" or export feature. The guide says to enforce limits on the back end or database, not in the screen.
- **Business logic abuse (WSTG-BUSL-01 to 07):** for a shared-care product, examples to think through are "can one family member see or change another family's record by editing an ID," "can a removed caregiver keep access," and "can a step in an invite flow be skipped." These are my mapping examples, not statements from the guide. WSTG-BUSL-03 (hidden fields and server-side checks) is the closest match to access-control logic.
- **CORS (WSTG-CLNT-07):** the guide warns against `*` and against echoing the Origin header. If the coordinator exposes an API to a browser app, this setting needs a deliberate choice.
- **Clickjacking (WSTG-CLNT-09):** the guide recommends the X-Frame-Options header, and a hosted site could set headers; the paper should note the newer `frame-ancestors` option is not covered by this guide, so it needs another source.
- **API testing and GraphQL (WSTG-APIT-01):** Supabase offers REST (PostgREST) and GraphQL, so the introspection, authorization, DoS and batching points apply in principle. The guide's GraphQL page is built around its own sample app, so it does not tell us how Supabase behaves. A separate Supabase source is needed.
- **Browser storage (WSTG-CLNT-12), TLS and unencrypted channels (WSTG-CRYP-01, CRYP-03):** health-adjacent family information should not sit in local storage, and traffic must use HTTPS. CRYP-03 lists healthcare and medical insurance information as examples of sensitive personal data.
- **Error handling (WSTG-ERRH-01):** generic errors matter more when the data is sensitive; stack traces would show the framework and database.

## Limits and cautions

- **Dated (2020).** Version 4.2 is the newest release but is about six years old. Browser behavior, TLS advice (for example TLS 1.0 and certificate lifespan rules) and tool lists have changed since.
- **Old technology.** The Flash page (WSTG-CLNT-08) is about a retired plug-in. Several clickjacking and CSS injection tricks target IE7/8, Opera and Safari 4. The XSSI IE9/10 error example is called "less relevant" by the guide itself.
- **Old tools named:** Tamper Data and Tamper Chrome, PadBuster, POET and similar padding oracle tools, Identity Finder, the Flash decompilers, and some links that may no longer work. I did not check the links.
- **The API chapter is very short:** only one page (GraphQL). There is no REST page in 4.2, so it cannot support claims about REST or PostgREST testing.
- **Some pages are thin or odd:** WSTG-ERRH-02 is a one-line stub; WSTG-CLNT-02, CLNT-03 and CLNT-13 have little or no remediation text; WSTG-CRYP-04 has unclear lines (for example about CBC and SSH, and ECB "in asymmetric encryption").
- **Not written for our stack.** Examples use PHP, Java, ASP.NET and classic servers. Mapping to Next.js, Supabase and Vercel is my reasoning, not the guide's.
- **No numbers or prevalence data.** The pages describe how to test; they do not say how common any flaw is.
- **No claim of safety.** Nothing here shows that the proposed coordinator is secure or compliant; these are test ideas to plan against.
