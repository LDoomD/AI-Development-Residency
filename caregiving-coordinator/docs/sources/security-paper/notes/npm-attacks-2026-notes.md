# Notes: The 2026 wave of self-spreading npm package attacks, and the npm and GitHub changes that followed

- **What this is:** the researchers' own write-ups (Socket, Aikido, Palo Alto Unit 42, StepSecurity, Snyk, JFrog, OX, Microsoft, and the TanStack maintainers' own post-mortem), plus GitHub's and npm's own notices and CISA's alerts. All pages were fetched on 2026-11-18 with plain `curl -L` (descriptive user agent, no header tricks) and read in full for the parts used below.
- **Labels for the paper:** the researcher write-ups are **tier 3, vendor research**. They are each company's own account of what it found, not standards. Several vendors sell security products. The GitHub, npm and CISA pages are tier 1 or 2 (platform owner, government), but they only describe their own actions and advice. They do not give package counts for the 2026 campaigns.
- **Local copies:** `caregiving-coordinator/docs/sources/security-paper/npm-attacks-2026/`. Each page is saved as `.html`. A plain-text copy (`.txt`) sits beside most of them. **Two text copies (Aikido's CanisterWorm page and StepSecurity's May 11 Mini Shai-Hulud page) disappeared from the folder right after I wrote them** (these pages print malware code; I did not confirm why). Their `.html` copies are still there and I read both pages in full another way.
- **Page numbers:** these are web pages with no page numbers. The "Source and heading" column names the page and its heading.
- **Rule for this file:** no malware code and no technical indicators beyond package names. Dates are UTC as the sources give them.
- **Words to avoid in the paper:** do not write that any of this makes a project "secure". The proposed coordinator is a product idea. It is not built. These notes show what attackers did to other projects.

## What the pages say (my words)

| What the pages say (my words) | Source and heading |
|---|---|
| A worm in this wave steals a developer's or CI job's publish credentials during `npm install`, then uses them to publish bad patch versions of every package that account can reach. It needs no further action from the attacker. | Aikido, "Technical Breakdown"; Unit 42 landscape, "The New Baseline for npm Threats" |
| In the first CanisterWorm wave the attacker ran the spreading script by hand with stolen tokens. About an hour later a new version harvested tokens from `.npmrc` files, environment variables and npm config, so it spread by itself. | Aikido, "Update: CanisterWorm Learns to Self-Propagate" |
| Socket says the attackers published the bad version with the `latest` tag so normal installs would pick it up. | Socket (CanisterWorm), "How the Attack Works" |
| CanisterSprawl's payload read `.npmrc`, SSH keys, cloud keys and `.env` files, sent them out, and tried to republish other npm packages and PyPI packages. Socket notes npm versions with no matching Git tags as a warning sign. | Socket (CanisterSprawl), "What the payload does"; "Why this looks like a compromise" |
| The TanStack attack needed no stolen password or token. Three known GitHub Actions weaknesses were chained and none was enough alone. | TanStack post-mortem, "Root cause" and "Why none alone is enough" |
| TanStack found out from outsiders about 20 to 26 minutes after the first bad publish. It had no alert on its own publishes. npm would not let it unpublish, so npm staff had to pull the files, which took about 3 to 4.5 hours. | TanStack post-mortem, "Detection and response", "Response timing", "Lessons learned" |
| The bad TanStack versions carried valid build-provenance records, because the real build pipeline ran. Provenance shows which pipeline built a file. It does not show the pipeline was clean. | StepSecurity (May 11), "TeamPCP's Mini Shai-Hulud Is Back"; Unit 42 landscape, "The SLSA Provenance Problem"; Socket (ChainDrop), "Recommendations" area |
| The May 19 wave went back to the simpler method: take over one maintainer account and republish. It added an install hook and bumped version numbers above the real latest, so loose version ranges such as `^2.x` pulled the bad version. | Unit 42 landscape, "May 19, 2026: @antv Wave" and "Infection Mechanism" |
| The counts for that wave differ: 637 versions (Snyk table), about 317 + 314 versions in Snyk's two waves, 639 versions (Unit 42), 640 packages removed (Microsoft). Snyk calls it a 22-minute burst; Unit 42 says about one hour. | Snyk, "TL;DR" and "Affected packages"; Unit 42 landscape; Microsoft, "How GitHub took action" |
| Several payloads set a "dead-man's switch": if the stolen GitHub token is revoked, the tool can wipe or run attacker code. So defenders are told to remove the watcher first, then rotate secrets. | Unit 42 landscape, "The Dead-Man's Switch"; Snyk, "Remediation, Step 1"; Socket (ChainDrop), "Recommendations"; StepSecurity (ChainDrop), "What you should do now" |
| IronWorm hid changes by forging old commit dates and using the names `claude`, `dependabot`, `renovate` and `github-actions`. JFrog says unusual changes from such names should be reviewed. | JFrog, "Finding infected repositories"; "For defenders" |
| In ChainDrop, many bad versions had no matching source commit, pull request or tag. Microsoft says this shows the attackers edited the package files directly instead of attacking each project's source code. | Microsoft (ChainDrop), overview section |
| Unit 42 found 453 public GitHub repos across five accounts that matched the worm's data-drop pattern, and saw it run in 10 environments. | Unit 42 (ChainDrop), "Executive Summary" |
| GitHub says that after Shai-Hulud in September 2025 it removed 500+ packages and then planned to allow only local publishing with 2FA or trusted publishing, drop old "classic" tokens, shorten token life and make "no tokens" the default. | GitHub blog, "Our plan for a more secure npm supply chain" (2025-09-22) |
| New write tokens last at most 90 days (default 7 days). Classic tokens were permanently revoked on 2025-11-19. New write tokens ask for 2FA unless "Bypass 2FA" is chosen. | GitHub changelog 2025-09-29 and 2025-11-05 |
| On 2026-05-19 npm cancelled every granular write token set to bypass 2FA, to stop attacks like the `@antv` wave. GitHub says to use trusted publishing. GitHub's page gives no count. | GitHub Community Discussion #196340 |
| npm v12 (July 2026) turned install scripts off by default and stopped installing from Git and plain web links unless allowed. | GitHub changelog 2026-06-09 and 2026-07-08 |
| A 2FA-bypass token could take over an account, add a maintainer and publish with no human present. Since 2026-07-31 such tokens cannot do account, team or package management. GitHub is targeting January 2027 to stop them publishing directly. | GitHub changelog 2026-07-31; Discussion #201329 |
| High-impact accounts that change email or use a 2FA recovery code go read-only for 72 hours, to stop "change email, mint token, publish." | GitHub changelog 2026-06-25 |
| npm says trusted publishing swaps stored write tokens for short-lived, one-job credentials. It recommends turning on "require 2FA and disallow tokens" once trusted publishing works, and "stage-only" publishing so a person approves each release. Self-hosted runners were "not currently supported." | npm Docs, "Trusted publishing for npm packages" |
| CISA's alerts say: pin versions, rotate all secrets, require phishing-resistant MFA, set `ignore-scripts=true`, set `min-release-age=7` (Axios alert) or wait three hours before pulling new packages (May 2026 alert), enable branch protection, secret scanning and Dependabot (Sept 2025 alert). | CISA alerts of 2025-09-23, 2026-04-20, 2026-05-28 |
| Unit 42's general fixes: wait 24 to 72 hours before using a new release, turn off lifecycle scripts, use `npm ci` with a lockfile, route installs through a private registry, verify provenance, limit outbound traffic from CI, and keep an SBOM for each release. | Unit 42 landscape, "Mitigations for Compromised npm Packages" |

## Useful for the paper

These are lessons from the sources, tied to the proposed coordinator's stack (Next.js, npm packages, GitHub Actions, Vercel). They are advice found in the pages, not proof that any project is safe.

- **Topic 5 (risks).** A project's own code can be fine while a dependency, or the build pipeline, is the way in. Most campaigns here hit packages that other projects install, with no change to the victim's own code.
- **Topic 5 (risks).** "Stolen publish tokens and CI accounts" is the common cause in most pages, but not all. TanStack says no token was stolen. The `@antv` account theft is "under investigation." CanisterSprawl's cause is "unresolved." The paper should say "mostly," not "always."
- **Topic 6 (trends).** The platform changed in response: classic tokens gone (Nov 2025), 90-day write tokens, bypass-2FA tokens cancelled (May 2026), install scripts off by default in npm v12 (July 2026), bypass-2FA tokens barred from account management (July 31, 2026), direct publishing by those tokens targeted for January 2027. Use dates exactly as GitHub's pages give them. The January 2027 date is a target.
- **Topic 7 (best practices), lockfiles and pinned versions.** Commit `package-lock.json`, use `npm ci` in CI, and pin exact versions. Socket, Unit 42, CISA, Microsoft and StepSecurity all say to pin. The `@antv` wave raised version numbers so loose ranges (`^`) pulled the bad version.
- **Topic 7, lifecycle scripts.** Almost every campaign here ran its code from an install hook. Check scripts, use `ignore-scripts` (Snyk, CISA, Microsoft) and, on npm v12, approve only the scripts you trust. This matters for the proposed coordinator because Vercel builds run `npm install`.
- **Topic 7, new-release delay.** CISA (3 hours; 7 days with `min-release-age=7`), Unit 42 (24 to 72 hours) and Microsoft (npm v12 `min-release-age`) suggest delaying new versions. Several bad versions were caught within 20 minutes to a few hours (TanStack about 26 minutes; Socket says its scanner flagged `keyv@6.0.0` within six minutes (from its tracker page, seen only as a search excerpt)).
- **Topic 7, short-lived credentials, 2FA, trusted publishing.** Keep secrets out of long-lived tokens. The proposed coordinator would only publish an npm package if it made one; most likely it only consumes packages. Still, its GitHub Actions secrets (deploy keys, Vercel tokens) are the same kind of target. Give CI jobs the least access, avoid `pull_request_target` on forks, and pin third-party actions to commit SHAs (TanStack's own lesson).
- **Topic 7, secret scanning and audit.** Rotate secrets after any suspect install, but remove any "token watcher" first (Snyk, Unit 42, Socket, StepSecurity). `npm audit` and GitHub's malware advisories (for example GHSA-g7cv-rxg3-hmpx) can flag known bad versions, but advisories can lag behind a fast worm (Unit 42 TeamPCP page).
- **Topic 7, watch your own publishes.** TanStack learned of the attack from outsiders. It says it needs alerts on its own releases.
- **Provenance is not proof.** Three sources (StepSecurity, Unit 42, Socket) say a valid provenance record can still sit on a bad release. The paper should not tell readers "check provenance" as a single fix.

## Limits and cautions

- **Counts differ and the paper must show the range, not one number.** CanisterWorm: 47 (Aikido, Unit 42) vs 135 files across 64+ packages (Socket, a day later). `@antv`: 637 vs 639 versions, 323 packages in both, "22 minutes" vs "about an hour." ChainDrop: "at least ten" (Socket, early), "more than 400" (Microsoft, Unit 42), 444 (StepSecurity), 447 (Socket tracker excerpt). The counts for ChainDrop and some others were still rising when the pages were written. Search results and news pages gave other figures (for example "1,300+" for ChainDrop, "172 packages across 404 versions" for Mini Shai-Hulud wave 1); I did not read those pages, so I do not use them.
- **These are vendor write-ups (tier 3).** Each describes what its own tools saw. Several sell protection. Two (Snyk's and Microsoft's) rely on other researchers for parts of the story. The 640-package and 61,274-token figures are Microsoft's statement about GitHub's action. GitHub's own post says tokens were invalidated but gives no count.
- **Campaigns were still being analyzed.** StepSecurity's ChainDrop page says "active investigation." Socket's CanisterWorm and CanisterSprawl pages say "developing." TanStack lists open questions. The Unit 42 landscape page is a living page "Updated July 15" and I did not see later edits.
- **Attribution is soft.** "TeamPCP" is the vendors' label. Unit 42 says the worm's code became public on May 12 and later waves may come from others. Name the group only as "attributed by" the vendor.
- **Names are community or vendor labels.** CanisterWorm (Aikido), ChainDrop (StepSecurity), CanisterSprawl (Socket). They are not official names.
- **GitHub's and npm's notices are plans and rules, not a measurement.** Four of the changelog pages (2025-09-29, 2025-11-05, 2026-07-08, 2026-07-31) show a "Retired" tag on GitHub's site; the pages do not say what that tag means. The January 2027 date is a target and not yet in force. The trusted-publishing page is a living document.
- **Nothing here proves a project is safe.** Following the advice lowers the chance of being caught by this kind of attack. It does not prevent it. The proposed coordinator is not built.
- **CISA did not publish an alert for any of the named 2026 campaigns that I could find** (see "Not read / not found"). The CISA alerts I saved cover other npm incidents.
