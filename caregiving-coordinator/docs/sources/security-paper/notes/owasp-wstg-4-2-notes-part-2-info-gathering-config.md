## What the pages say (my words)

### 4.1 Information Gathering

| What the pages say (my words) | Test ID and section |
|---|---|
| Search engines and archives can show things the owner never meant to publish. The tester looks for network diagrams, staff emails, login steps and username formats, passwords and private keys, cloud config files, revealing error text, and test or staging copies of the site. | WSTG-INFO-01, "Test Objectives" and "How to Test" |
| Testers use search operators (`site:`, `inurl:`, `intitle:`, `filetype:`) and cached copies, and chain them in a method called "Google hacking" or dorking. Public databases of ready-made dorks exist. Do not rely on one search engine, because results differ. Shodan searches internet-connected devices. | WSTG-INFO-01, "Search Operators", "Viewing Cached Content", "Google Hacking, or Dorking" |
| Fix: think about how sensitive design and config details are before posting them, and review what is already posted on a schedule. A `robots.txt` file or a "noindex" meta tag can keep pages out of search, but only if kept up to date. | WSTG-INFO-01, "Summary" and "Remediation" |
| Fingerprinting a web server means finding its type and version so the tester can look up known flaws for that version. Methods: read the response headers (banner grab), guess from header order when the name is hidden, send a broken request and compare the error page, and use scanners (Netcraft, Nikto, Nmap). | WSTG-INFO-02, "How to Test" |
| Showing the server name is not a flaw by itself, but it helps an attacker. Fix: hide server info in headers, put a hardened reverse proxy in front, and keep the server patched. | WSTG-INFO-02, "Remediation" |
| Metafiles leak the site map. `robots.txt` lists paths the owner wants crawlers to skip, which can point a tester straight at them. Crawlers can ignore it, so it is not a way to restrict access. Meta tags, `sitemap.xml`, `security.txt`, `humans.txt` and other `.well-known/` files can also show paths, technology, and contacts. | WSTG-INFO-03, "Robots", "META Tags", "Sitemaps", "Security TXT", "Humans TXT", "Other .well-known Information Sources" |
| The tester checks which applications sit on one server. One IP address can host many apps through: a different base URL (not at `/`), a non-standard port (full port scan with Nmap), and virtual hosts (several DNS names on one IP). Ways to find names: DNS zone transfer (mostly refused today), reverse DNS, web DNS-search services, reverse-IP services, and search engines. | WSTG-INFO-04, "Test Objectives" and "Approaches to Address Issue 1, 2 and 3" |
| The page warns that apps seen as "internal only" are often left unpatched or misconfigured. | WSTG-INFO-04, "Summary" |
| Page content can leak data. Developers leave HTML comments with SQL queries, passwords, or internal IPs. Front-end JavaScript can hold hard-coded API keys, internal addresses, hidden admin routes, or credentials. When a key is found, the tester checks whether it is restricted (by service, IP, or referrer). | WSTG-INFO-05, "Review webpage comments and metadata" and "Identifying JavaScript Code and Gathering JavaScript Files" |
| Source map files connect minified front-end code back to the original code. If they are live in production, the code is easy to read and bugs are easier to find. The tester adds `.map` to each script URL to check. The guide says whether to ship them is a judgment call for a security expert. | WSTG-INFO-05, "Summary" and "Identifying Source Map Files" |
| Before deeper testing, the tester maps every entry point: each URL, query parameter, POST body field, hidden field, custom header, and cookie, and notes if each needs login or uses TLS. Rare methods (PUT, DELETE) are noted. A spreadsheet plus an intercepting proxy is the suggested way. | WSTG-INFO-06, "How to Test", "Requests", "Responses" |
| With source code access (gray-box), the OWASP Attack Surface Detector can list endpoints and parameters from the code, including unlinked ones a crawler would miss. | WSTG-INFO-06, "Gray-Box Testing" and "OWASP Attack Surface Detector" |
| Testers cannot test every code path, so they record which ones they covered. Three coverage ideas: path testing, data-flow (taint) testing, and race testing. How much of each is agreed with the app owner. A spider (for example ZAP) helps list pages. | WSTG-INFO-07, "How to Test", "Automatic Spidering" |
| Fingerprinting the framework means finding clues in headers (`X-Powered-By`, `X-Generator`), cookie names, HTML source, default files and folders, file extensions, and error messages. Tools: WhatWeb, Wappalyzer, and forced browsing ("dirbusting"). | WSTG-INFO-08, "Black-Box Testing", "Common Identifiers", "Tools" |
| Changing cookie names, hiding paths, or removing headers is "security through obscurity" and only slows basic attackers. Time may be better spent on staff awareness and keeping software up to date. | WSTG-INFO-08, "Remediation" |
| WSTG-INFO-09 has no content of its own. It says it was merged into WSTG-INFO-08. | WSTG-INFO-09 |
| Before reviewing configuration, the tester maps the architecture: firewall, reverse proxy, load balancer, app server, database, and login back end (LDAP, RADIUS). Many can be spotted from banners, odd error pages, cookies (JSESSIONID, F5 BIGipServer), and timing of cached responses. The page says a single weak point can undermine the whole setup. | WSTG-INFO-10, "Summary" and "Map the Application Architecture" |

### 4.2 Configuration and Deployment Management Testing

| What the pages say (my words) | Test ID and section |
|---|---|
| Check the settings of every part of the setup (web server, database server, login server) and look for known vulnerabilities. Scanners that go by version number give false alarms and misses (for example when a Linux vendor patches an old version number), and often cannot see back-end parts. Unsupported old software gets no patches. Keep a list of needed ports under change control. | WSTG-CONF-01, "Summary" and "Known Server Vulnerabilities" |
| Admin tools (for content, code, user databases, servers) need review too: how access is controlled, and change default usernames and passwords. When a vendor manages part of the site, admin interfaces are often exposed to the internet, so test them. | WSTG-CONF-01, "Administrative Tools" |
| Remove default and sample files, test pages, and debug code before going live. Use configuration checklists such as CIS-CAT Lite, Microsoft Attack Surface Analyzer, and the NIST National Checklist Program. | WSTG-CONF-02, "Test Objectives", "Sample and Known Files and Directories", "System Configuration" |
| Server hardening guidance: turn on only needed modules, use custom error pages (never show stack traces or code), run the server with the least privilege, log access and errors, handle overload, and (for IIS) lock down the config files and any shared-config share. | WSTG-CONF-02, "Configuration Review" |
| Logging checks: no sensitive data in logs (passwords, session IDs, tokens, keys, payment data, even less sensitive personal data such as emails and phone numbers), logs on a separate server, no way to fill the disk, rotation that follows the policy, tight access (users and even web admins should not see raw logs), and review of 40x and 50x error spikes to spot attacks. The page notes that personal data in logs can bring data protection law duties in some places. | WSTG-CONF-02, "Logging", "Sensitive Information in Logs", "Log Location", "Log Storage", "Log Rotation", "Log Access Control", "Log Review" |
| Some file types must never be served (`.asa`, `.inc`, `.config`). Others (archives, `.txt`, `.pdf`, Office files, `.bak`, `.old`) should be checked to see if they are leftovers with secrets. The page's example is an `.inc` file that returned database credentials in plain text. Also check every server behind a load balancer, since they may differ. | WSTG-CONF-03, "Forced Browsing" and "Example" |
| File upload filters can be fooled by Windows 8.3 short names (for example `SHELL~1.PHP`). | WSTG-CONF-03, "File Upload" |
| Forgotten backups are a leak: `.old`, `.bak`, `~` editor copies, zip archives, "Copy of" files, log files, and file system snapshots in the web folder. A `.old` copy of a script may be served as plain text, showing its code and passwords, or still hold an already-fixed bug. Testers guess names from the site's naming pattern, read comments and `robots.txt` for clues, brute-force common names, and use old search engine results. | WSTG-CONF-04, "Summary", "Threats", "Black-Box Testing" |
| Fix for old and backup files: do not edit files in place on a production server, do not leave archives behind, use configuration management, keep data, log and config files outside the web-served folders, and block snapshot folders. A scheduled script can look for backup-style file names. | WSTG-CONF-04, "Remediation" and "Gray-Box Testing" |
| Admin interfaces may exist but be hidden. Testers guess paths (`/admin`), read code comments and links, check default docs and default passwords, try other ports, and check for tricks such as a hidden form field or cookie like `admin=no`. Gray-box review checks that admin pages are not open to everyone (for example IP filtering), no default credentials remain, and normal users and admins are separated in code and in shared UI parts. | WSTG-CONF-05, "Black-Box Testing" and "Gray-Box Testing" |
| Most apps need only GET and POST. Testers list which HTTP methods work (Nmap `http-methods`), try PUT to upload a file, try odd methods (`HEAD`, made-up ones) to get past login checks, test TRACE (cross-site tracing), and test method-override headers (`X-HTTP-Method-Override` and similar). For REST services, each endpoint should accept only the methods it needs. | WSTG-CONF-06, "Test Objectives" and "How to Test" |
| The page says the TRACE attack only works in recent browsers if the app also uses technology like Flash. | WSTG-CONF-06, "Testing for Cross-Site Tracing Potential" |
| Fix for methods: allow only the methods and headers that are needed, and add no workarounds that skip security controls. | WSTG-CONF-06, "Remediation" |
| HSTS is a response header that tells the browser to use only HTTPS for the site (`max-age`, `includeSubDomains`, and an unofficial `preload`). It helps against network sniffing, man-in-the-middle attacks, and users who type or click an `http://` address. The test is to confirm the header is present, for example with `curl`. | WSTG-CONF-07, "Summary" and "How to Test" |
| RIA policy files (`crossdomain.xml`, `clientaccesspolicy.xml`) control cross-domain access for Flash, Java and Silverlight. A wildcard `*` policy is too open, can defeat CSRF protection, and can expose data. The test is to fetch the files and check them against least privilege. | WSTG-CONF-08, "Summary", "Impact of Abusing Cross-Domain Access", "How to Test" |
| Files and folders given wider permissions than needed can leak or be changed. Check web files, config files, key and password files, logs, executables, database files, temp files, and upload folders (`ls`, `namei`). Fix: set permissions so unauthorized users cannot reach them. | WSTG-CONF-09, "Summary", "How to Test", "Remediation" |
| Subdomain takeover: a DNS record points to a service or domain that is no longer in use, and someone else claims it. The examples are an old GitHub Pages record, an expired domain behind a CNAME, and an NS record to an expired domain (the highest impact, since it can give control of the whole zone). Impact includes malicious content, phishing, and stealing cookies or credentials. Test: list DNS records and look for NXDOMAIN, SERVFAIL, or REFUSED answers. Fix: delete dead DNS records and keep checking. | WSTG-CONF-10, "Summary", "How to Test", "Remediation" |
| Cloud storage test: find the storage URL (for example in an `img` tag), then try to read data and upload a file without permission. The page uses Amazon S3 as its example. The page says S3 buckets are private by default and become exposed when someone grants public access to a bucket or object. Other cloud storage can have similar risks. Tool: curl or the AWS CLI. | WSTG-CONF-11, "Summary", "How to Test", "Testing for Amazon S3 Bucket Misconfiguration" |

## Limits and cautions

- **Dated.** Version 4.2 is from 2020-12-03. v5.0 is in development. Some pages predate current practice. Check the paper's claims against current docs for any specific product.
- **Old tools and examples.** Several named tools and technologies are old or niche: Flash, Silverlight, Java applets (CONF-08, whose whole subject is Flash/Silverlight-era policy files), IIS 5 and 8-era guidance, Lotus Domino, iPlanet, Sam Spade, Netsparker dictionary, Net Square, Google Webmaster Tools (INFO-03), Nessus, and "Attack Surface Detector 1.3.5". Reference lists in CONF-02 cite 2000 to 2005 documents.
- **Page-specific cautions.** CONF-08 (RIA cross-domain policy) is mostly obsolete for a modern stack; I would not cite it as a current best practice. CONF-06's XST (TRACE) attack is described as working only in older browsers or with Flash-like tech. INFO-03 says `robots.txt` is not an access control, which is useful to cite, but its example robots files are from 2020.
- **Product-neutral.** The pages do not mention Next.js, Supabase, Vercel, row-level security, or health data. All stack-specific points above are my own mapping and need separate sources.
- **A testing guide, not proof.** Nothing here shows that any product is secure. It says what a tester checks. The paper must not write that the proposed coordinator is "secure" or "compliant" because it follows these checks.
- **Legal point is brief.** CONF-02 says personal data in logs may bring data protection law duties "in some jurisdictions"; it does not name a law. Do not cite it for HIPAA or GDPR specifics.
- **Many of the sample values in the pages are fake or from public sites** (for example the White House and Google examples, sampled 2020-05-05). They are illustrations, not findings.
