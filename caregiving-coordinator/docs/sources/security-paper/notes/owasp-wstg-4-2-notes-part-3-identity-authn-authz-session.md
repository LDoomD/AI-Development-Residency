## What the pages say (my words)

| What the pages say (my words) | Test ID and section |
|---|---|
| **Roles.** Apps give people roles (admin, auditor, support, customer). The test is to list the roles, try to switch to another role, and check each role is no stronger than needed. Fuzz clues include cookie values like `role=admin` and hidden `/admin` paths. Finding that roles exist is not a flaw if the app protects them. A support worker should not do admin work or act as the user. Even an admin should not have unchecked full power: risky admin actions should need a second person ("maker-checker") or MFA. The page cites a 2020 Twitter incident as an example. Tools named: Burp Autorize, ZAP Access Control Testing add-on. | WSTG-IDNT-01, "Test Role Definitions" (Test Objectives; Review Roles Permissions) |
| **Registration.** Check who can sign up, whether a person vets sign-ups, whether one person can register twice, whether people can ask for higher roles, what proof of identity is needed, and whether identity data can be faked or changed in transit. Fix: match the identity checks to how sensitive the protected data is. | WSTG-IDNT-02, "Test User Registration Process" (How to Test; Remediation) |
| **Provisioning and de-provisioning.** Find which roles can create other accounts and what kind. Ask: is there a check on create and delete requests; can an admin create another admin; can anyone create an account stronger than their own; can someone delete themself; what happens to the deleted person's files (deleted or handed over). The page has no Remediation section. | WSTG-IDNT-03, "Test Account Provisioning Process" (How to Test) |
| **Account enumeration.** Check whether the app tells an attacker which usernames exist. Compare the reply (text, page title, length, redirect URL, error code, timing) for a real user with a wrong password versus a fake user. A password reset form that says "user not found" also leaks. A 403 versus 404 on user pages leaks too. Response time can leak when a real user triggers an email. Guessable user IDs (sequential, or first initial plus last name) make it worse. Testing may lock accounts. Fix: the same generic error for every failed login; delete default and test accounts before release. | WSTG-IDNT-04, "Testing for Account Enumeration and Guessable User Account" (HTTP Response Message; Other Ways to Enumerate Users; Guessing Users; Remediation) |
| **Username policy.** Account names often follow a pattern (first initial plus surname), so they can be guessed. Test whether the pattern and the error messages allow enumeration. Fix: consistent generic error messages. | WSTG-IDNT-05, "Testing for Weak or Unenforced Username Policy" |
| **Credentials in transit.** Capture traffic and confirm that logins, sign-ups, password change or reset, and every logged-in request use HTTPS, even when a tester forces `http://`. The session cookie must carry the `Secure` flag. Fix: HTTPS for the whole site, HSTS, redirect all HTTP to HTTPS. If that is hard, start with the sensitive actions. Encrypted does not mean safe: the cipher and keys also matter (the page points to the weak-TLS test). | WSTG-ATHN-01, "Testing for Credentials Transported over an Encrypted Channel" (How to Test; Remediation) |
| **Default credentials.** Test common apps and devices for factory logins, and test whether new accounts get a guessable starting password that users never change. Try names like admin, test, or the app name. Look for passwords hidden in page source, comments, backups, config files, or hard-coded in code. Warns that guessing can lock the admin account. Tools named: Burp Intruder, THC Hydra, Nikto. The page lists causes: staff who never change defaults, left-behind back doors, undeletable built-in accounts, no forced change after first login. | WSTG-ATHN-02, "Testing for Default Credentials" (Summary; Testing for Default Password of New Accounts; Gray-Box Testing) |
| **Lockout.** Lockout stops password guessing and code guessing (2FA, security questions). It is a balance: too strict locks real users out. The page says accounts are typically locked after 3 to 5 failures and that a 5 to 10 range is a typical threshold. A 5 to 30 minute lockout is called a reasonable compromise. A CAPTCHA can help but should not replace lockout, and the page lists ten ways CAPTCHA is often broken. The unlock path (emailed link, security questions) needs a one-time link and is not the same as password recovery. Manual admin unlock can be abused to lock everyone out. Remediation ladder, low to high assurance: timed unlock, self-service email unlock, admin unlock, admin unlock with positive ID. | WSTG-ATHN-03, "Testing for Weak Lock Out Mechanism" (Lockout Mechanism; Unlock Mechanism; Remediation) |
| **Bypassing authentication.** Check that every protected page enforces login: forced browsing to a page directly, changing a parameter like `authenticated=no` to `yes`, guessing or predicting session IDs, and SQL injection in the login form. The gray-box example is an old phpBB bug where a crafted cookie skipped the password check. The page says flaws can start in design, development, or deployment. No remediation section. | WSTG-ATHN-04, "Testing for Bypassing Authentication Schema" (Black-Box Testing; Gray-Box Testing) |
| **Remember-me and password managers.** "Stay logged in" and autofill add risk. Credentials should not be stored in the browser at all (use server-made tokens instead). Autofill can be abused by clickjacking and CSRF. Tokens that never expire are dangerous if stolen. Fix: follow session management good practice; store passwords only server-side with proper password storage. | WSTG-ATHN-05, "Testing for Vulnerable Remember Password" (How to Test; Remediation) |
| **Browser cache and history.** Sensitive pages should not stay in the browser cache or the Back button after logout. Check response headers for `Cache-Control: no-cache, no-store`, `Expires: 0` and `Pragma: no-cache`; `must-revalidate, max-age=0` is suggested as an extra. Test mobile browsers separately. This matters on shared computers. | WSTG-ATHN-06, "Testing for Browser Cache Weaknesses" (Browser History; Browser Cache; Check Handling for Mobile Browsers) |
| **Password policy.** Check allowed characters, length limits, how often and how fast a password can be changed, reuse (history of 8 is mentioned), differences from the last password, bans on the username inside the password, and whether weak passwords like `Password1` are allowed. It says NIST and the UK NCSC recommend against forced regular expiry, though PCI DSS may require it. Remediation: a strong policy (length, complexity, reuse, aging) and, ideally, two-factor authentication too. | WSTG-ATHN-07, "Testing for Weak Password Policy" (How to Test, item 3; Remediation) |
| **Security questions.** Pre-made questions (mother's maiden name, favorite color, first school) have answers that family can know, that can be guessed, brute-forced from name lists, or found on social media. User-made questions are often worse ("What is 1+1?"). The scheme is only as strong as its weakest question. Check how many wrong guesses are allowed. | WSTG-ATHN-08, "Testing for Weak Security Question Answer" (Pre-generated Questions; Self-generated Questions; Testing for Brute-forcible Answers) |
| **Password change and reset.** Check that nobody except admins can change or reset another person's password, that the flow cannot be tricked into resetting someone else's, and that it is protected from CSRF. For reset: asking only for an email link means 100% trust in that mailbox (not enough for high-security apps); showing the new password on screen is the worst case; sending the old password means passwords are not hashed; a random token link that the user must click keeps the old password valid until confirmed. For change: require the current password, since a hijacked session could otherwise take over the account. Fix: ask the user to log in again or confirm. | WSTG-ATHN-09, "Testing for Weak Password Change or Reset Functionalities" (How to Test; Test Password Reset; Test Password Change; Remediation) |
| **Weaker alternative channels.** Mobile sites, old or test versions, partner sites, apps, call centers and phone systems may use the same accounts with weaker checks. The example is a mobile site with no TLS and a weaker password recovery. The test is to list the channels, compare each login function in a grid, and test them like the main site. Call centers may check identity more weakly. Also check whether cookies or sessions overlap across channels. Fix: one consistent authentication policy on all channels. | WSTG-ATHN-10, "Testing for Weaker Authentication in Alternative Channel" (Summary; Enumerate Authentication Functionality; Remediation) |
| **Directory traversal and file include.** If a parameter or cookie picks a file, an attacker may use `../` (and many encodings) to read files outside the allowed folder, or include files from other sites. Test every input that touches files; try encodings, and watch for weak "clean-up" filters. In gray-box tests, search code for file-include functions. No remediation section. | WSTG-ATHZ-01, "Testing Directory Traversal File Include" (Input Vectors Enumeration; Testing Techniques; Gray-Box Testing) |
| **Bypassing authorization (horizontal and vertical).** Horizontal: two users with the same role; swap parameters and session tokens and see if one sees the other's data. Vertical: use a lower role's session to call higher-role functions (the page's bank example: customer, staff, manager, admin). Checking only in the screen (GUI) and not in the function is a common flaw. Also test access without login, after logout, and to resources of another role (the page's example is files in an S3 bucket). It also covers headers like `X-Original-URL` and `X-Forwarded-For` that can get around front-end rules. Fix: least privilege. Tools named: ZAP Access Control Testing, AuthMatrix, Autorize. | WSTG-ATHZ-02, "Testing for Bypassing Authorization Schema" (Horizontal; Vertical; Administrator Page Access; Special Request Header Handling; Remediation) |
| **Privilege escalation.** Check that a user cannot change their own role or group. Tests: edit group or order IDs in a request, edit hidden profile fields like `profile=SysAdmin`, edit status values the server trusts, fake an `X-Forwarded-For` IP, traverse URLs, partial URL matching (`startswith`, `contains`) in the code, and weak session IDs such as a hash of password plus user ID. Defines vertical escalation (more privilege) and horizontal escalation (another similar user's data). No remediation section. | WSTG-ATHZ-03, "Testing for Privilege Escalation" (Summary; Testing for Role/Privilege Manipulation; Weak SessionID) |
| **Insecure direct object references (IDOR).** The app uses an ID from the request (invoice number, user name, file name, menu item) to fetch or change something without checking that this user may. Test with at least two users and swap the other user's object IDs. Four cases: database record, an operation (for example, "change password for user X"), a file, or a menu function. IDOR is often combined with path traversal. No remediation section. | WSTG-ATHZ-04, "Testing for Insecure Direct Object References" (Summary; How to Test and four sub-scenarios) |
| **Session tokens: randomness and structure.** Collect many tokens, check they are random, not time-based, and not built from readable data (the page shows a token that hides a username and password in plain, hex, Base64 or MD5 form). Check brute-force room: longer and more varied IDs with shorter life are harder. Gray-box points: no predictable inputs such as IP; the page says at least 50 characters, a set time-out, and cookies kept in memory only, Secure, and HttpOnly. Tools named: ZAP session analysis, Burp Sequencer. | WSTG-SESS-01, "Testing for Session Management Schema" (Cookie Collection; Session Analysis; Cookie Reverse Engineering; Brute Force Attacks; Gray-Box Testing) |
| **Cookie attributes.** Explains each: `Secure` (HTTPS only), `HttpOnly` (script cannot read it; does not stop all XSS harm), `Domain` and `Path` (keep narrow so other apps or sub-domains cannot read it), `Expires`, and `SameSite` (Strict, Lax, None; Strict can force re-login from emailed links; None needs Secure). Prefixes `__Host-` and `__Secure-` make the browser enforce settings. Its strongest example: `__Host-SID=<token>; path=/; Secure; HttpOnly; SameSite=Strict`. | WSTG-SESS-02, "Testing for Cookies Attributes" (Cookie Attributes; Cookie Prefixes; Strong Practices) |
| **Session fixation.** If the session cookie stays the same before and after login, an attacker who plants a known cookie in the victim's browser can take over after the victim logs in. Fix: issue a new session ID after login, and invalidate the old one first. Also use full HSTS or `__Host-` / `__Secure-` cookie prefixes against network attackers. The page gives an 11-step test with victim and attacker accounts. | WSTG-SESS-03, "Testing for Session Fixation" (Summary; Test with Forced Cookies; Remediation) |
| **Exposed session variables.** Session IDs must travel only over encrypted channels, never in a GET URL (logs and links expose them), and should not be cached (`Cache-Control: no-cache`; `private` still allows non-shared caching; add `Expires: 0` and `max-age=0`). Check that a POST-only page does not accept the same data by GET. A new session token should come after every login. | WSTG-SESS-04, "Testing for Exposed Session Variables" (Encryption and Reuse; Proxies and Caching; GET and POST; Transport) |
| **CSRF.** If the app trusts only what the browser sends by itself (cookies, HTTP auth), a hostile page, email image tag, or auto-submitted form can trigger actions as a logged-in user. Using POST alone does not fix it. JSON APIs can be hit with a plain-text form. It can work from inside a private network. Webmail-style apps can be both the carrier and the target. The page gives only a pointer for prevention (the OWASP CSRF Prevention Cheat Sheet, not read). | WSTG-SESS-05, "Testing for Cross Site Request Forgery" (Summary; How to Test; Remediation) |
| **Logout.** Logout has to end the session on the server, not only clear the browser cookie. A logout button should be on every page and easy to see. Test by logging out, then pressing Back, reloading, and replaying the old cookie. Some frameworks keep no server state, so an old cookie still works (the page names ASP.NET Forms Authentication). Single sign-on needs both logouts to end all sessions. Short sessions also reduce XSS and CSRF risk. The page says a bank should not keep an idle session over 15 minutes while a forum may use an hour or more. | WSTG-SESS-06, "Testing for Logout Functionality" (Summary; Log Out User Interface; Server-Side Session Termination; Session Timeout; Single Sign-Off) |
| **Session time-out.** Every app needs an idle time-out, enforced on the server, not from a client cookie value. It is a trade between safety and ease and depends on data sensitivity (15 minutes for home banking, 60 for a public forum, as examples). If an attacker already holds a session, idle time-out does not stop them if they keep it active. Gray-box: invalidate on the server (for example `HttpSession.invalidate()`); clearing the cookie is good but not strictly needed. | WSTG-SESS-07, "Testing Session Timeout" (Summary; Black-Box Testing; Gray-Box Testing) |
| **Session puzzling.** The same session variable is used for two purposes (for example a password-reset page sets "who you are" and a private page trusts it). An attacker visits pages in an unplanned order. Hard to find from outside; code review is best. Fix: each session variable has one purpose. | WSTG-SESS-08, "Testing for Session Puzzling" (Summary; Gray-Box Testing; Remediation) |
| **Session hijacking.** An attacker with the session cookie becomes the user. Cookies need `Secure` even if the whole site uses HTTPS (an injected HTTP request can leak them). With a loose `Domain` attribute, HSTS must cover all sub-domains (full HSTS, `includeSubDomains`) or a fake sub-domain can capture the cookie. The page gives a 10-step test with victim and attacker accounts. | WSTG-SESS-09, "Testing for Session Hijacking" (Summary; How to Test) |
| **Section lists (READMEs).** The four README files only list the tests in each chapter (4.3 Identity Management, 4.4 Authentication, 4.5 Authorization, 4.6 Session Management). 4.3 has five tests, 4.4 has ten, 4.5 has four, 4.6 has nine. | READMEs in folders 03, 04, 05, 06 |

## Useful for the paper

Mapped to the eight paper topics (numbers as in the task: 1 intro, 2 career, 3 what the field covers, 4 methods and tools, 5 risks, 6 trends, 7 best practices, 8 application to the proposed coordinator).

- **Topics 1 and 3 (intro, what the field covers).** These four chapters show that web security testing is split into who you are (identity), proving it (authentication), what you may do (authorization), and keeping the login alive safely (sessions). This is a plain way to describe part of the field.
- **Topic 2 (career).** The pages describe tester work: two-account tests, proxy tools, source review in gray-box mode. Tools named: OWASP ZAP, Burp Suite (Autorize, AuthMatrix, Sequencer), THC Hydra, Nikto, curl. This supports a short "what a web security tester does" paragraph. (It does not describe pay or demand; use other sources for that.)
- **Topic 4 (methods and tools).** Black-box versus gray-box testing; intercepting proxies; two-user comparison tests; session token analysis; cookie jar snapshots.
- **Topic 5 (risks and challenges), and flags for the proposed caregiving coordinator:**
  - **IDOR (WSTG-ATHZ-04).** A care-circle record fetched by an ID in the URL could be read by someone outside the circle if the server does not check membership. Strongest fit for the proposed coordinator.
  - **Privilege escalation and role definitions (WSTG-ATHZ-02, ATHZ-03, IDNT-01).** The proposed roles (primary caregiver, family member, outside helper) are the kind of roles these tests check. Vertical test: can an outside helper do primary-caregiver actions? Horizontal test: can a helper in one care circle see another circle? The "role in a cookie or hidden field" warning applies to anything the client can edit.
  - **Role and provisioning (WSTG-IDNT-02, IDNT-03).** Who can invite a new member, whether an invited person can be given a stronger role than the inviter, and what happens to shared data when a member is removed. The page asks the same last question about a de-provisioned user's files.
  - **Account enumeration (WSTG-IDNT-04, IDNT-05).** Invite and sign-in screens that say "no such email" would reveal who is in a care circle. This is a privacy risk in a health-adjacent setting.
  - **Password reset (WSTG-ATHN-09).** Reset by email link relies fully on that mailbox; the page says that is weak for high-security apps. Family members may share email accounts, so this matters.
  - **Session fixation (WSTG-SESS-03), hijacking (SESS-09), cookies (SESS-02), logout (SESS-06), time-out (SESS-07), CSRF (SESS-05).** Shared family devices and tablets make logout, idle time-out, cache and Back button (WSTG-ATHN-06) real concerns.
  - **Shared credentials.** The pages say credentials should not be stored in browser storage and that default or shared starter passwords are risky (WSTG-ATHN-02, ATHN-05). They do not talk about a product that stores other people's logins for the user; that needs another source.
- **Topic 7 (best practices) from these pages:** generic login errors; HTTPS plus HSTS everywhere; new session ID at login; invalidate sessions on the server; `Secure`, `HttpOnly`, `SameSite`, `__Host-` cookie settings; least privilege; ask for the current password before a change; check access on the server for every request, not only in the screen.
- **Topic 8 (application to the proposed coordinator).** Planned stack is Next.js, Supabase (Postgres with row-level security) and Vercel. These pages are written for any web app and do not mention those products. Any mapping (for example, "row-level security is the place to enforce care-circle membership, so a tester can try IDOR against it") is **my inference, not something the pages say**. Mark it as such in the paper.
- **Topic 6 (trends).** Little here; the pages show older practice. Use newer sources for trends.

## Limits and cautions

- **Dated 2020.** Released 2020-12-03; v5.0 is in development. Many external references are older (RFC 2965 and RFC 2616 are obsolete; some sample dates are from 2006 and 2008; the phpBB example is from the early 2000s). Tool lists include Internet Explorer and FireSheep, and the "HTTPS Everywhere" extension, which are out of date.
- **Password advice that is older than NIST SP 800-63B-4 and ASVS 5.0.0 (both newer; I did not re-read them in this task, so the contrast below is from the task brief, not from my own reading of those two documents):**
  - **WSTG-ATHN-07** says the simple fix is a "strong password policy" covering length, **complexity**, reuse and **aging**, and asks about required character sets. Newer guidance, as given in the task brief, says no composition rules and no forced rotation. Note that the same WSTG page, in item 3, does already say NIST (the 800-63-3 edition) and NCSC recommend against forced expiry, so the page contradicts itself between item 3 and the Remediation paragraph. Also, a "history of 8 passwords" check and "how different the next password must be" are older ideas. Cite WSTG for how to test, not for what the rule should be.
  - **WSTG-ATHN-08** accepts security questions as a feature and only asks to test their strength. Newer guidance (as I understand it, to be checked in SP 800-63B-4) treats knowledge-based questions as not acceptable for authentication. Verify before writing this in the paper.
  - **WSTG-ATHN-03** gives 3 to 5 failed attempts as typical in the summary but 5 to 10 in the remediation. The numbers are loose; do not quote them as a rule.
  - **WSTG-ATHN-09** says reset by email is the "best security" option in its list. That ranking is only among the options listed. It is still a single-mailbox trust, as the same page notes.
  - **WSTG-SESS-01** gives "at least 50 characters" and "256-bit AES" as gray-box points. These look like loose rules of thumb, not a standard. Check against ASVS before citing.
  - **WSTG-SESS-02** says `SameSite=None` is a recommended value over leaving it unset. Browser defaults have changed since 2020; check current browser behavior before repeating this.
- **Two typos or inconsistencies seen in the pages (so you do not quote them wrongly):** in ATHZ-02, the horizontal example shows `viewSettings` and then the attacker request uses `viewCCpincode`; in IDNT-04 the figures jump from 4.3.4-1 to 4.3.4-3; in ATHZ-04 the file example says `img` in the URL but `file` in the text.
- **Tester guide, not a design standard.** Remediation is short, and several pages (ATHN-04, ATHZ-01, ATHZ-03, ATHZ-04, IDNT-03) have no remediation section. For "what to build" use ASVS and the OWASP cheat sheets (not read here).
- **Not about this stack.** Nothing here covers Supabase row-level security, Next.js, Vercel, JWT or OAuth-based sessions, passkeys, or MFA beyond mentions. Do not claim this source proves anything about the proposed coordinator's safety. It supplies test ideas only. Never write that the proposed coordinator is secure or compliant.
- **Quote budget:** this notes file uses one short quote: a security question scheme is "only as strong as the weakest question" (WSTG-ATHN-08).
