## Security Glossary

<image source="notion-file-block://2199219a-4691-828e-8866-81b4c88f8efd/84b88e7e-de61-4147-8a59-cd07990e11d6?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-glossary.png" />

### Let’s talk “Security”

<b>Info Security Glossary</b>

<b>Attack surface</b>

All the places where someone could try to get into or misuse your app. Every page, form, login, file upload, API, and outside service adds to it. The bigger it is, the more you have to protect.

<b>Attack vector</b>

The path or method an attacker uses to get in. Examples are a fake email, a form that accepts harmful input, or a stolen password.

<b>Authentication</b>

Checking who someone is. Logging in with a password, a code sent to your phone, or a passkey are all ways to authenticate.

<b>Authorization</b>

Checking what someone is allowed to do once you know who they are. It always comes after authentication. A student can see their own grades but cannot change them.

<b>Confidentiality, Integrity, Availability (CIA)</b>

The three goals of information security. Confidentiality means only the right people can see the data. Integrity means the data is correct and nobody changed it without permission. Availability means the app and its data are there when people need them.

<b>Defense in depth</b>

Using several layers of protection, so if one layer fails, another one still stops the attack.

<b>Encryption</b>

Scrambling data so only someone with the right key can read it. HTTPS encrypts data while it moves. A database can encrypt data while it is stored.

<b>Information security</b>

Protecting information from being seen, changed, or destroyed by people who should not have it. It covers data wherever it lives: on paper, on computers, or moving between them.

<b>Least privilege</b>

Giving every person and every part of the app only the access it needs to do its job, and nothing more.

<b>Network security</b>

Protecting the connections between computers and the data that moves across them. It includes firewalls, encrypted connections like HTTPS, and blocking traffic that should not get in.

<b>Penetration testing</b>

A planned attack on your own app, with permission, by a security tester. The goal is to find weak spots before a real attacker does. The tester writes down what they broke and how to fix it.

<b>Risk</b>

How likely a threat is to use a vulnerability, and how bad the damage would be if it did. Teams fix the biggest risks first.

<b>Secure coding principles</b>

Rules for writing code that is hard to attack. Use safe ways to talk to the database. Give each part only the access it needs. Keep secrets out of the code. When something fails, fail in a safe way.

<b>Security policy</b>

A written set of rules for how a team keeps its information safe. It says who can access what, how passwords and data must be handled, and what to do when something goes wrong.

<b>Threat</b>

Anyone or anything that could cause harm to your app or data. That could be an attacker, a mistake by a teammate, or a server going down.

<b>Threat modeling</b>

Planning ahead for how someone could attack your app. You list what you need to protect, who might attack it, how they could do it, and how you will stop them. You do it before you build, and again when the app changes.

<b>Vulnerability</b>

A weakness in your code, settings, or process that an attacker could use. Not every bug is a vulnerability, but many vulnerabilities start as bugs.

## Fundamental Security Principles

<image source="notion-file-block://75d9219a-4691-836c-9e3c-016a9f348570/33956bc7-3cd6-41b4-8e60-34cb614d754f?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-principles.png" />

### Information Security Principles

<b>Never Trust the User</b>

This is the most important rule in web security, and it means you treat everything a user sends as a possible attack. An attacker can change anything their browser sends, like form boxes, web addresses, and hidden fields. So the server must check every piece of input on its own. It should never let the browser decide what someone is allowed to do. If you skip this rule, one changed value can let a stranger pay less, see private data, or take over the app.

<b>Apply the Principle of Least Privilege</b>

Least privilege means every person, account, and program gets only the access it needs to do its job. A support worker who answers questions does not need the power to delete accounts. In the same way, the app does not need full control of the database just to read orders. When a team follows this rule, a stolen login can only do a small amount of harm. When a team skips it, one break-in can open up everything.

<b>Secure Over Multiple Layers (“Defense In Depth”)</b>

Defense in depth means you protect the same thing in more than one place, so one failure does not let the attacker in. Think of a bank that has a locked door, a guard, cameras, and a safe, and not just one of them. In an app, you might check input when it arrives and check it again right before it is used. No single defense is perfect, so stacking them keeps one mistake from turning into a disaster.

<b>Security Through Obscurity</b>

Security through obscurity means trying to stay safe only by hiding how your system works. One example is using a secret web address for the admin page and adding no other lock. Hiding things does not stop attackers, because they have tools that hunt for hidden pages all day long. Keeping details private can help a little, but only when real locks like strong logins are already in place. If hiding is your only defense, someone will find the way in.

<b>Fail Safely</b>

Failing safely means that when something goes wrong, the app should lock down instead of opening up. If the app hits an error it did not expect, it should stop what it was doing and show no private data. It should also treat the person as having no access until things are fixed. A bad example is a login check that crashes and then lets the person in anyway. If you skip this rule, attackers can cause errors on purpose to slip past your locks.

### Defense Categories

<b>Train Your Employees</b>

People are often the easiest way into a company, so training them is one of the strongest defenses you have. Good training shows people how to spot fake emails, fake calls, and fake login pages. It also teaches them what to do when something feels wrong, and to never share passwords or codes. A team that knows these tricks can stop a social engineering attack before any technology has to.

<b>Secure Coding</b>

Secure coding means building the app so that its own code does not leave openings for attackers. The team checks all input on the server and uses safe ways to talk to the database. They build things in ways that make many attacks much harder, and they never put sensitive data into the code itself. This protects against many attacks across many layers. But, like any of these, it’s not the only thing that’s needed!

<b>Secure Network Configuration</b>

Secure network configuration means setting up the paths between computers so only the right traffic gets through. The team turns on HTTPS everywhere so data is locked while it travels. They use firewalls to block traffic that does not belong, and they keep the database off the open internet. They also limit how many requests one person can send at once. This protects against listening in, faked messages, and attacks that flood the server.

<b>Secure Files</b>

Secure files means controlling which files people can upload, where those files are kept, and who can open them. The team checks every upload for its type and size before saving it. They store uploads away from the files that run the app, and they never let users pick the folder. They also keep backups and secret keys out of any place the public can reach. This blocks file tampering and file theft, and it keeps one bad upload from taking over the server.

<b>Secure Permissions</b>

Secure permissions means deciding who can see and do each thing in the app, and then checking it every time. The server checks permission on every request, and each account gets only the access its job needs. The team also removes old accounts and changes any default passwords that came with the software. This stops people from reaching pages, records, or settings that belong to someone else, even when they have a real login.

<b>You can’t only have one of these: you need all of them! “Defense In Depth” means you use many layers of protection at once.</b>

## Confidentiality, Integrity, Availability (CIA)

<image source="notion-file-block://0c19219a-4691-8277-8278-0157cc0c5bc4/a72c2448-c1a5-456f-8ea3-412a01011d8c?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-cia.png" />

<b>What Is the CIA Triad?</b>

CIA stands for Confidentiality, Integrity, and Availability, and these are the three things information security tries to protect. Every attack on the board hurts at least one of them, and many attacks hurt more than one. When you plan how to keep an app safe, ask three questions about each piece of data. Who should be able to see it, is it correct, and will it be there when people need it?

<b>Confidentiality</b>

Confidentiality means only the right people can see the data. In our restaurant, Evil Cake Corp attacks confidentiality when they sneak into the kitchen and copy our secret cake recipes. They might also steal the list of our customers' names and home addresses. In a real app, this looks like a data leak, where someone reads private messages or card numbers they should never see. Once private data gets out, you can never fully take it back.

<b>Integrity</b>

Integrity means the data is correct and nobody changed it without permission. Evil Cake Corp attacks integrity when they swap our sugar for salt or change the oven settings. They might also trade our cake for an evil cake on the way to the customer. In a real app, this looks like someone changing prices, grades, or bank balances in the database. Changed data can look normal, so people may trust it for a long time before anyone notices.

<b>Availability</b>

Availability means the app and its data are there when people need them. Evil Cake Corp attacks availability when they lock up our kitchen and hold it hostage. They might also flood us with 10,000 fake orders so we can't serve our real customers. In a real app, this looks like an attack that makes the site crash, or ransomware that locks up all the files. Even if nothing is stolen or changed, a business that can't serve anyone still loses money and trust.

### Here’s how the Software Layers and Network Layers Can Be Attacked

### You and Your Computer

Your internet browser, desktop application, or mobile application

<b>Layers</b>

Software Layer: Presentation

Network Layer: Client

<b>Attack Surfaces</b>

Internet Browser software

HTML / CSS / Javascript

Code libraries (Like React, GH repo code, etc.)

The user interface

You, the human!

Web Extensions

<b>Attack Vectors</b>

<b>SESSION / COOKIE HACKS</b>

When you log in, the website gives your browser a small pass called a cookie. This pass lets you move around the site without typing your password on every page. An attacker can steal that pass with a bad link, bad code on a page, or an unsafe public Wi-Fi network. Then they put it in their own browser, and the website thinks they are you. They can see your account and do anything you can do, all without your password.

<b>VULNERABILITIES INSIDE CSS / HTML / JS</b>

HTML, CSS, and JavaScript are the code that builds the page you see and makes its buttons work. Weak spots in that code can be turned against the people who use the page. An attacker might hide a button you can't see on top of a real one. They might also slip bad code into a tool that the page loads from another company. Then your clicks and typing go where you did not mean them to, so you might pay for something or give away your password.

<b>AUTHENTICATION AND AUTHORIZATION HACKS</b>

Authentication is how an app checks who you are, and authorization checks what you are allowed to do. Attackers get past the first check by guessing passwords or using ones leaked from other sites. They get past the second check by going to pages the app was never meant to show them. When either check fails, a stranger can take over a real account and see or change things that belong to someone else.

<b>SOCIAL ENGINEERING</b>

Social engineering means tricking a person instead of breaking the tech, since people are often the easiest way in. An attacker might send a fake email that looks like it came from your bank. They might call and pretend to work on your IT team, or build a fake login page that looks real. Once you hand over a password or a code, the attacker can walk right past every lock the team built.

<b>CROSS-SITE SCRIPTING</b>

Cross-site scripting happens when an attacker sneaks their own code into a website. The code then runs in your browser as if the website itself had sent it. Attackers often hide the code in a link, a search box, or a comment that the site shows without checking it first. Because your browser trusts the website, the code can steal your login pass, change what you see, or do things in your name.

### “The Internet”

The communication between your computer and the server that allows you to load websites, use apps, and see data from other places inside your own computer.

<b>Layers</b>

Software Layer: Service

Network Layer: “The Middle Layer” Between all layers! (Client → Server → Database)

<b>Attack Surfaces</b>

APIs

HTTP Requests

Webhooks

Your internet router

<b>Attack Vectors</b>

<b>HTTP REQUEST TAMPERING</b>

Every time you click a button, your browser sends a message to the server called an HTTP request. An attacker can catch that message on their own computer and change it before it leaves. For example, they might change a price, a user number, or a hidden setting. If the server trusts the message without checking it, the attacker can pay less, see other people's data, or give themselves more power.

<b>PROXY ATTACKS</b>

A proxy is a computer that sits between you and a website and passes your requests along. Many proxies also save copies of pages so they load faster for everyone. An attacker can trick a proxy into saving a fake copy of a real site. They can also set up their own proxy and get people to send their traffic through it. Then everyone who uses that proxy may get a fake page that shows false facts, spreads bad code, or collects what people type.

<b>API ATTACKS</b>

An API is a door that lets apps and computers ask a server for data or tell it to do something. It works behind the scenes, without the screens a person sees. Attackers go straight to that door and send their own requests, like changing an account number to pull up someone else's records. They may also send thousands of requests to see what slips through. If the API does not check who is asking and how often, it can leak private data for many users at once.

<b>“MAN IN THE MIDDLE” ATTACK</b>

In a man in the middle attack, someone secretly gets between you and the website, so your data passes through them. This often happens on public Wi-Fi at a coffee shop or an airport. The attacker may set up a fake network, or watch data that is not locked with HTTPS. They can read your passwords and messages, or quietly change what is sent, and nobody can tell.

<b>REQUEST FORGERY</b>

Request forgery tricks your browser into sending a request to a site you are logged into, without you knowing. An attacker hides the request inside another page, an email, or an image. Just opening it makes your browser act for you, with your login attached. The website thinks you asked, so it may send money, change your email, or delete your data.

<b>AI PROMPT INJECTION</b>

Prompt injection tricks an AI tool by giving it hidden orders that make it ignore the rules its builders gave it. An attacker can type these orders straight into a chat. They can also hide them inside a web page, a file, or an email that the AI is asked to read. The AI may then share private facts, give harmful answers, or use its tools to do things that nobody meant to allow.

### The Web Server

These computers hold your internet app files, handle requests from the client layer, and make requests to the database server to pull and edit data.

<b>Layers</b>

Software Layer: Domain

Network Layer: Server

<b>Attack Surfaces</b>

Server configuration

Server computer OS

Server permissions

Business logic scripts

Server Programming Languages (PHP, Python, etc.)

Files

<b>Attack Vectors</b>

<b>FILE TAMPERING</b>

Many apps let people upload files like photos, and the server also keeps its own files that make the app run. An attacker might upload a bad file that looks normal, or send huge files to fill up the space. They might also trick the app into opening files outside the folder it should use. This can let the attacker read private files, change how the app works, or take over the whole server.

<b>DENIAL OF SERVICE</b>

A denial of service attack tries to make an app so busy that it stops working for real people. Attackers flood the server with more requests than it can handle, often from thousands of hacked computers at once. They may also send requests that take a very long time to finish. While the attack goes on, people cannot log in or buy anything, and the business loses money and trust.

<b>INJECTION</b>

Injection happens when an app takes what a person types and hands it to another program on the server without checking it. An attacker types commands where normal text should go, like in a name box or a search box. The program follows those commands as if the app had sent them. The attacker can then run their own commands on the server, read data they should not see, or break the app.

<b>FILE THEFT</b>

Servers keep many files that should stay private, like customer uploads and backup copies. Some of these files even hold passwords or secret keys. An attacker might guess the web address of a file, or trick the app into handing over files from the wrong folder. Once those files are out, the attacker can read private records, log in to other systems, and sell what they took.

### The Database Server

These computers are dedicated to storing the data and handling requests from the web server to pull and edit data.

<b>Layers</b>

Software Layer: Data Source + Database

Network Layer: Database

<b>Attack Surfaces</b>

Database software

SQL

Data records

Database permissions

Files

Database configuration

<b>Attack Vectors</b>

<b>SQL INJECTION</b>

SQL is the language an app uses to ask the database for facts, like one shopper's orders. In SQL injection, an attacker types bits of SQL into a normal form, such as a login box or a search box. The database then runs those bits as part of the real question. The attacker can log in without a password, read every record, or change and delete data.

<b>DATA TAMPERING</b>

Data tampering means changing saved facts without permission, like prices, grades, or bank balances. An attacker can do this through a weak spot like SQL injection. They can also use an account that has more power over the database than it needs. The damage can be hard to spot, and once people learn the data was changed, they can no longer trust what the app shows.

<b>STORED CROSS-SITE SCRIPTING</b>

Stored cross-site scripting happens when an attacker saves harmful code in the database, often in a comment or a profile. Later, the app pulls up that saved post and shows it to every visitor. Each visitor's browser runs the hidden code without them doing anything at all. One saved post can reach thousands of people, steal their logins, or spread the attack to more pages.

<b>DATA THEFT</b>

Data theft means someone reads or copies data they were never allowed to see, like names, emails, or card numbers. An attacker might use SQL injection or steal a login that has too much access. They might also find a database that was left open to the internet. Stolen data can be sold, used to trick people, or posted online, and the business can lose the trust of its users.

### All About OWASP

<b>Who Is OWASP?</b>

OWASP stands for the Open Worldwide Application Security Project, a nonprofit group that started in 2001. It is a worldwide community of people who want to help others build software that is safe to use. Everything OWASP makes is free and open to everyone, so any team can use it without paying. Because so many experts help write and check its work, many teams treat it as a trusted guide.

<b>What Does OWASP Focus On?</b>

OWASP focuses on application security, which means keeping apps and websites safe from attacks. Its goal is to make software safer by teaching people, sharing free tools, and getting people to work together. This matters because many attacks go after the app itself, like its forms and logins, and not just the network. OWASP helps builders who are not security experts learn how to close those gaps.

<b>What Is the OWASP Top 10?</b>

The OWASP Top 10 is a list of the ten biggest security risks for web apps, and the newest one came out in 2025. It names risks like people reaching things they should not, unsafe settings, weak logins, and injection attacks. Many teams use it as the main list to check their apps against, and it is a good place to start.

<b>What Is the OWASP Cheat Sheet Series?</b>

The OWASP Cheat Sheet Series is a free set of short guides, and each one covers a single security topic. There are more than 100 of them, on topics like logins, passwords, file uploads, and AI tools. Security experts write each guide, and it tells you what to do in clear steps, a bit like a recipe card. The Top 10 tells you what the biggest risks are, and the cheat sheets tell you how to guard against them.

<b>How Do Product Teams Use the Cheat Sheets?</b>

Product teams use the cheat sheets like a checklist while they plan and build a feature. If a feature has a login, the team opens the login cheat sheet and turns its steps into acceptance criteria. Those then become test scenarios, so the team can prove each guard works before they launch. Teams can also tell their AI coding tools to follow a cheat sheet, and then check the code against it during review.

## OWASP Security Testing Framework

<image source="notion-file-block://4c09219a-4691-8279-b113-81db752fcbdf/b4ba6917-e083-42a7-82f6-a404a4e5398f?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-testing-framework.png" />

The OWASP Security Testing Framework is a plan from OWASP for testing security at every stage of building an app, not just at the end. OWASP says to treat it as a flexible guide that each team shapes to fit the way it works. Testing only after the app is built costs more, and OWASP says a final hacking test on its own is not good at finding most bugs.

### PHASE 1: Before You Build

Get ready before any work starts. Threat model, research the potential vulnerabilities, prepare the approach.

<b>1.1 Set up your process</b>

Plan how you will build the app, with a security step built into every stage.

<b>1.2 Check your rules</b>

Make sure the team has written security rules, like how to code safely, before work starts.

<b>1.3 Decide what to measure</b>

Pick how you will measure security now, so you can collect that data as you go.

### PHASE 2: While You Plan and Design

Check the plan before you build it. In this class, this is where threat modeling and security requirements happen.

<b>2.1 Review the security requirements</b>

Read the security rules closely and fix any gaps or rules that could be read two ways.

<b>2.2 Review the design</b>

Check that the design can really meet the security rules, since design mistakes are cheap to fix now.

<b>2.3 Draw how the app works</b>

Make diagrams of how the app works and check them with the people who designed it.

<b>2.4 Make threat models</b>

List real ways the app could be attacked, and make sure each one is fixed, accepted, or handed to another company.

### PHASE 3: While You Build

Check the code while it is being written. In this class, this is where secure coding and CI / CD checks happen.

<b>3.1 Walk through the code</b>

Developers explain how their code works, so reviewers understand it before the real review.

<b>3.2 Review the code</b>

Reviewers read the code and check it against security checklists, like the OWASP guides.

### PHASE 4: When You Launch

Check the finished app and how it is set up. In this class, this is where the How to Test checks happen.

<b>4.1 Run a penetration test</b>

Testers try to break into the finished app, as one last check for anything that was missed.

<b>4.2 Check the setup</b>

Review how the servers and software were set up, so no risky starter settings are left on.

### PHASE 5: After Launch

Keep checking for as long as the app is running. Run security testing and pentesting to ensure that you are not able to hack the system.

<b>5.1 Review how the app is run</b>

Keep a written plan for how the app and its servers are run every day.

<b>5.2 Run regular security tests</b>

Check the app every month or every few months to catch any new security risks.

<b>5.3 Check every change</b>

After each update goes live, check that it did not make the app less safe.

<b>5.4 Monitor your network and software</b>

After each update goes live, monitor things to catch any events as they are happening.

## Threat Modeling

<image source="notion-file-block://8629219a-4691-83b5-bc20-8157f666921a/4bc2a85f-56d7-47ba-aabc-0e1714956c6f?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-threat-modeling.png" />

### What is Threat Modeling?

Threat modeling is how a team plans for attacks before they build. The team looks at a feature the way an attacker would and asks what could go wrong and how to stop it. It is a team effort, so everyone on the product team takes part. The product manager explains what the feature is for and what data it touches, and the designer shows how people will move through it. Developers explain how the parts connect, QA plans how to test each fix, and a security expert helps spot threats the team might miss.

The best time to do it is during design, before anyone writes code, and again any time the app changes. It is worth the time because problems cost far less to fix early. A study by NIST found that a problem caught after launch can cost about 30 times more to fix than one caught at the start. Some harm, like stolen data, can never be undone at all.

### How to Threat Model

1. <b>Draw what you are building.</b> Make a simple map that shows who uses the feature, the screens, the server, and the database. Draw arrows for the data that moves between them. Mark every spot where data crosses into a new layer, since that is where attacks often happen.
2. <b>List what you need to protect.</b> Write down everything worth stealing, changing, or breaking, like customer data, payments, passwords, and the app staying online. Then tie each one back to Confidentiality, Integrity, or Availability so you know what kind of harm to watch for.
3. <b>Ask what could go wrong.</b> Go through your map one part at a time and think like Evil Cake Corp. Use the attack vectors from each layer to list the ways someone could steal, change, or break what you are protecting.
4. <b>Rank each threat.</b> For each threat, ask how likely it is and how bad the damage would be. Work on the threats with the highest risk first, so your time goes where it matters most.
5. <b>Decide what to do and write it down.</b> For each threat, choose to fix it, remove the part that causes it, hand the risk to another company, or accept it. Turn every fix into acceptance criteria and BDD scenarios, and write down why you accepted any risk you did not fix.
6. <b>Check your work and do it again.</b> After the fixes are built, test them to make sure they really stop each threat. Update your threat model any time the feature changes, because new parts can bring new threats.

## Security Deliverables for Head Chefs

<image source="notion-file-block://4559219a-4691-8380-98f9-814ad4df29d9/ef4f1eca-31bc-4c4a-b1f8-c050817d0076?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-produce.png" />

### What Should Product Teams Produce for Defense In Depth?

<b>CI / CD Pipelines that Catch Code Vulnerabilities</b>

A CI / CD pipeline is a set of automatic checks that runs every time someone changes the code. For security, the team adds checks that scan for weak spots, passwords left in the code, and add-ons with known holes. If any check fails, the change is blocked and can't go live until someone fixes it. This layer catches mistakes that people miss, and it never gets tired or skips a step.

<b>Secure Code</b>

Secure code is code written to follow safe rules from the very start, using guides like the OWASP Cheat Sheets. It checks every input on the server, talks to the database in a safe way, and keeps secrets out of the code. Before it is added to the app, another person or an AI tool reviews it to look for mistakes. This layer stops many attacks at the source, because the weak spot never gets built.

<b>Requirements</b>

Security requirements are the written rules that say how a feature must protect people and their data. The team writes them during planning, often from the threat model, and turns them into acceptance criteria and BDD scenarios. For example, a login feature might require the account to lock for 15 minutes after five wrong passwords. Because the rules are written down, everyone builds and tests toward the same goal, and nothing important is left to memory.

<b>Security Testing Reports</b>

A security testing report shows the results of trying to break the app on purpose, the same way an attacker would. It can come from scanning tools, from the team's own tests, or from an outside expert who is paid to break in. Each report lists what was found, how serious it is, and how to fix it. After the fixes, the team tests again to prove the holes are closed and that no new ones were added.

<b>Security Configurations on Servers, Files, and Software</b>

These are the settings that decide how safe your servers, files, and software are while they run. The team turns off features the app does not use and removes the starter accounts and passwords. They keep all software up to date, and they lock down who can read or change each file and folder. They also keep error messages from showing too much about how the app works inside. Writing these settings down as a checklist lets the team set up every server the same safe way.

### How to Make Security Requirements

<image source="notion-file-block://79e9219a-4691-838a-a3d1-818034387178/f2f0848d-806d-411f-87a5-eb3303eb6522?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-requirements.png" />

Security requirements are written rules that say how a feature must keep people and their data safe. They turn the threats you found into clear rules the whole team can build and test. The product manager often leads this work, with help from designers, developers, QA, and a security expert. You write them during planning, right after threat modeling and before anyone starts to build. Good rules are clear enough that anyone can tell if they pass or fail.

<b>Steps</b>

1. <b>Start from your threat model.</b> Pull up the list of threats you ranked and the fixes you chose. Each fix you decided to build becomes at least one rule, so nothing you planned gets lost along the way.
2. <b>Check the OWASP Cheat Sheets.</b> Find the cheat sheet for each part of your feature, like logins, file uploads, or passwords. Use its advice to fill in gaps that your team may not have thought of on its own.
3. <b>Write rules that never trust the user.</b> Find every place a user can send data, like forms, web addresses, and cookies. For each one, write a rule that the server must check the data before it is used. Anyone can change what their browser sends, so your rules should never let the browser decide what someone can do.
4. <b>Write each rule in plain words.</b> Write one clear rule for each protection, like "Lock the account for 15 minutes after five wrong passwords." Stay away from vague words like "secure" or "safe," because nobody can test them.
5. <b>Add the rules to your acceptance criteria.</b> Put each rule into the feature's acceptance criteria, so the feature is not done until every rule passes. This puts safety in the same place as every other rule, where no one can miss it.
6. <b>Write BDD scenarios for each rule.</b> Write a Given, When, Then scenario for each rule, and include the path an attacker would take. For example, Given a user has typed five wrong passwords, When they try again, Then the account is locked for 15 minutes.
7. <b>Review the rules and keep them current.</b> Have the whole team, including a security expert, read the rules before building starts. Update them any time the threat model changes, so the rules always match the real risks.
8. <b>Turn every rule into a CI / CD check.</b> Your security protocol and your BDD scenarios must each become a check in the CI / CD pipeline. Then every rule gets tested each time the code changes, and a change that breaks a rule can't go live.

### How to Code Securely

<image source="notion-file-block://0ad9219a-4691-83ae-acb2-81dfb5bf7b0d/8277e819-818a-47f8-b545-9345b4080fe4?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-code-securely.png" />

Coding securely means writing code that follows the OWASP Cheat Sheets and the software patterns your team chose, so weak spots never get built. Developers do most of this work, but product people and QA help by writing clear rules and checking the results. Today a lot of code is written with AI tools, so the team must give those tools the same cheat sheets and patterns. This happens every time someone writes or changes code, not just once at the end.

<b>Steps</b>

1. <b>Find the cheat sheets for your feature.</b> Before you write any code, find the OWASP cheat sheets that match what you are building, like the one for logins or file uploads. Give them to your AI coding tool too, so every line it writes follows the same rules.
2. <b>Follow the software patterns you chose.</b> Build each security check into the pattern and layer you picked in your architecture, so each check lives in one place. When a rule lives in one place, every part of the app uses it, and nobody makes a weaker copy.
3. <b>Presentation layer: clean what you show.</b> In the screens, turn anything a person typed into plain text before you show it, so hidden code can never run. The OWASP Cross Site Scripting Prevention Cheat Sheet shows how to do this.
4. <b>Domain layer: check who can do what.</b> Put the checks for who is allowed to do each thing in the domain layer on the server, and never only in the screens. The OWASP Authorization Cheat Sheet shows how to check permission on every request.
5. <b>Data source layer: use safe queries.</b> In the code that talks to the database, keep what a user typed apart from the database command. The OWASP SQL Injection Prevention Cheat Sheet shows how to write these safe queries.
6. <b>Keep secrets and errors private.</b> Store keys and passwords in a safe vault and never in the code, and show users short error messages while the details go to a private log. The OWASP Secrets Management and Error Handling Cheat Sheets show how.
7. <b>Never describe your logic in browser comments.</b> Comments in the code that runs in the browser, like HTML and JavaScript, can be read by anyone who clicks View Source. Never leave notes there about how your checks work, test passwords, other servers, or bugs you have not fixed yet. Keep those notes in the server code or in private team documents, where attackers can't see them.
8. <b>Turn your coding rules into CI / CD checks.</b> Each safe coding rule you follow, like safe queries and no secrets in the code, must also become a check in the CI / CD pipeline. Then the pipeline stops any change that breaks a rule, even when a person or an AI tool missed it.

### How to Make CI / CD Pipelines for Security

<image source="notion-file-block://3b19219a-4691-8345-bc05-012842c67b34/47795953-b8b2-422e-8646-87ea1e9b0158?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-cicd.png" />

A CI / CD pipeline is a set of checks that runs on its own every time someone changes the code. Three things must become checks here: your secure coding principles, your security protocol, and your BDD scenarios. Together they work like a guard at the door that stops unsafe code from going live. Developers usually set it up, but the whole team decides what should block a release.

<b>Steps</b>

1. <b>Run your security tests on every change.</b> Add the BDD scenarios from your security requirements to the pipeline, so they run every time the code changes. If any scenario fails, the change cannot go live.
2. <b>Scan the code for weak spots.</b> Add a tool that reads the code and looks for known unsafe patterns, like typed input that goes straight into the database. These tools can catch mistakes before the code ever runs.
3. <b>Check your add-ons for known holes.</b> Add a tool that checks every outside package your app uses against a list of known security holes. When it finds one, it tells you which update fixes the problem.
4. <b>Scan for leaked secrets.</b> Add a check that looks for passwords, keys, and other secrets hidden in the code. If one is found, block the change and replace that secret right away, since someone may have already seen it.
5. <b>Make the checks block, not just warn.</b> Set every security check so a failure stops the change from going live. A check that only shows a warning is easy to ignore, and ignored warnings are how holes reach real users.
6. <b>Watch the results and keep improving.</b> Look at what the checks catch, and add new checks when you find new kinds of problems. Each time a mistake slips through, add a check so the same mistake cannot get through again.

3. Leave the app alone for a while. It should log you out on its own.

1. Put your page inside a frame on a test page. It should refuse to load.
2. View the page source and look for secrets or notes in the comments.
3. List every outside script the page loads and check each one for known holes.

<b>TESTING AGAINST AUTHENTICATION AND AUTHORIZATION HACKS</b>

1. Enter a wrong password five times. The account should lock for a while.
2. Try the default usernames and passwords that came with the software. None should work.
3. Log in as one user and change the web address to open another user's page. You should be blocked.
4. Open admin pages as a basic user. You should be blocked.

2. Send staff a practice fake email and track who clicks or replies.
3. Call the help desk as a fake user and see if they check who you are.
4. Coach anyone who was fooled, then run the test again later.

1. Type a harmless test script into every text box and web address.
2. Check that it shows up as plain text and never runs.
3. Run a scanner tool that tries many tricks at once.

Source: OWASP Testing Guide 4.7.1 and 4.11.1, and the Cross Site Scripting Prevention Cheat Sheet

<b>TESTING AGAINST HTTP REQUEST TAMPERING</b>

3. The server should reject or ignore the change.

3. Confirm every page loads over HTTPS, so no proxy can swap in a fake.

Source: OWASP Testing Guide 4.4.6 and 4.9.1

<b>TESTING AGAINST API ATTACKS</b>

1. Call the API directly, without going through the app's screens.
2. Change an ID in the request to another user's. It should be blocked.
3. Call it without logging in. It should refuse.
4. Send many requests fast. It should slow you down after a limit.

Source: OWASP Testing Guide 4.5.2 and 4.5.4, and the REST Security Cheat Sheet

<b>TESTING AGAINST “MAN IN THE MIDDLE” ATTACK</b>

1. Run an online TLS scanner on your site to find weak settings.
2. Open the site with http:// and check that it jumps to https://.
3. Check that no page sends passwords or loads scripts over plain HTTP.

Source: OWASP Testing Guide 4.2.7, 4.9.1, and 4.9.3

<b>TESTING AGAINST REQUEST FORGERY</b>

1. Build a test page on another site with a hidden form that sends a request to your app.
2. Log in to your app, then open the test page in the same browser.
3. The action should fail, because the request is missing its safety token.

Source: OWASP Testing Guide 4.6.5

<b>TESTING AGAINST AI PROMPT INJECTION</b>

1. Type orders like "ignore your rules" straight into the chat.
2. Hide orders inside a file or web page the AI is asked to read.
3. Check that it never shares private data or does things it should not.
4. Save these tests and run them again after every change.

Source: OWASP LLM Prompt Injection Prevention Cheat Sheet. This is not in the Testing Guide.

## PenTesting

<image source="notion-file-block://9939219a-4691-827c-ab2d-017b87c61711/0d8b15e6-f506-4cb3-94b1-1e5fd8d1d521?space_id=86b8f0f5-4593-44ca-8943-86ae19d3fdd5&name=wk6-pentesting.png" />

### What Is PenTesting?

PenTesting is short for penetration testing. It is a planned attack on your own app, done with permission, to find weak spots before a real attacker does. The tester acts like Evil Cake Corp and tries the attack vectors at every layer, from the browser all the way to the database. Then they write down what they broke, how bad it is, and how to fix it. The OWASP Testing Framework puts this test near launch as one last check, not the only one, because a pentest alone can miss problems that earlier checks would catch. In this class, you will security test a codebase and write up what you find in a PenTest Report.

<b>Background</b>

Explain why this test is happening and what the app is for. Say who asked for the test, when it was run, and who ran it. Keep it short, so any reader can follow the rest of the report.

<b>Code Being Tested</b>

Share a link to the codebase, a link to the live app, and a short description of what the app does. Name its main parts, like the screens, the server, and the database, so readers know exactly what was tested.

<b>Scope of the Test</b>

List what you tested and what you left out. In this class, the test covers the OWASP Cheat Sheet Series risks for your Week 4 app. It covers all five software layers, from presentation to the database, and all three network layers: client, server, and database.

<b>PenTest Audit</b>

Before you look for problems, list every test you plan to run, with one row for each test. For each one, name the software layer and the network tier it checks, the OWASP risk it covers, and the steps to run it. Start from the How to Test checks on this board, so no layer gets skipped.

<b>Findings</b>

Log each problem as its own row, with a name and a severity from P0 Critical to P3 Low. Note the software layer and the network layer where it lives, the weak spot behind it, and what could happen if an attacker used it. Then add the secure coding and network security principles to apply, and the OWASP cheat sheets to read.

<b>Recommendations</b>

Write a numbered list of fixes, with the most severe problems first. Each fix should say what to change and which finding it solves, so the team can turn it straight into a task.

<b>BDD</b>

Write BDD scenarios that will prove each fix works when we code and test again. For example, Given a user is logged out, When they open another user's page, Then they are sent to the login page. Add these scenarios to your CI / CD pipeline as checks so the same problem can never come back.
