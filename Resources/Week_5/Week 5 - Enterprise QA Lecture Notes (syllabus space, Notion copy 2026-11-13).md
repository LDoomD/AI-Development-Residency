## QA Glossary

[image not saved]

### Let’s talk “QA”

**Acceptance Criteria**

The plain, clear rules that say when a feature is done and correct. They turn a requirement into something you can mark pass or fail.

**Autotest**

Tests that a computer runs for you from a saved script. They are fast, and they run the same way every time. Best for checks you repeat on every build.

**BDD**

Short for Behavior Driven Development. It writes each path through a feature in a fixed Given, When, Then shape, so everyone reads it the same way. Each line becomes a test you can check.

**CI / CD**

Short for Continuous Integration and Continuous Delivery. The app is tested automatically on every change, and it is always kept ready to go live.

**DevOps**

A way of working where the people who build the app and the people who run it work as one team, with no wall between them.

**Hot Fix**

A release that fixes a serious problem right away, without waiting for the next planned release.

**Manual Testing**

A person runs the test by hand and uses their own judgment. It is the best way to catch things a script was never told to look for, like a screen that is confusing or a layout that looks wrong.

**New bugs**

A new bug is something that is broken and was never right in the first place. Example: the very first time you tap Save, nothing happens at all.

**Quality Assurance**

The work of making sure the app does what it should, and does it well, for every user. It is bigger than just testing.

**Regression**

When something that used to work stops working after a change. Regression testing checks that this did not happen.

**Smoke Testing**

A quick, light check right after a new build to see if it is stable enough to test more. It does not try every feature. It just checks that the app opens and the most important paths work.

**TDD**

Short for Test Driven Development. You write the test first, then just enough code to pass it, then clean it up. People call this red, green, refactor.

**Technical Debt**

The extra work you take on later because the code was built in a quick or messy way now. Like a loan, it charges interest over time.

**Test Case Scenario**

One exact thing to check, with the setup, the steps, and the result you expect. It is specific enough that anyone can run it and get the same answer. You build it from a BDD scenario.

**Test Coverage**

How much of your code or your requirements your tests actually check. Low coverage means big parts of the app are never tested. Teams often set a line it must not drop below.

**Unit Testing**

Tests one small piece of code on its own, like one function. These run the fastest and cost the least to write, so you want the most of them.

**Use Cases**

One path a person takes through a feature. You write the happy path, where everything goes right, and the non-happy paths, where something goes wrong.

## Types of QA Testing

[image not saved]

**Types of QA Testing**

There are many kinds of quality assurance tests that serve different purposes! All of these are used in combination with each other on Enterprise Development teams. Robots, humans, and scripts work together to provide “test coverage”.

## Martin Fowler’s Testing Pyramid

[image not saved]

**Martin Fowler’s Testing Pyramid**

A QA test is a check that proves the app does what it should. The testing pyramid is a picture that shows how many of each kind of test to write.

Unit tests are at the bottom because you have the most of those in your system. A unit test checks one tiny piece of code by itself, like the part that adds up a total. They are fast and cheap, so you want the most.

You want less integration tests and less end-to-end tests because they require the most time and energy for teams. They are more complex to run and require more checks. You do not want to automate many of the end-to-end and integration tests because it will slow down every single code push you do in your development environment.

### Types of Test Coverage

**End-to-End tests**

QA testers check the entire sequences from each layer: presentation, domain, service, data source

**Integration tests**

QA testers check the connection between one system and another system

**Unit tests**

QA testers check to make sure the functionality that was planned actually works according to ADRs, requirements, and standards.

## What You Try to Catch

[image not saved]

**What You Try to Catch**

**New bugs**

A new bug is something that is broken and was never right in the first place. Example: the very first time you tap Save, nothing happens at all.

**Regressions**

A regression is when something that used to work stops working after a change. Example: you add a new filter, and now the old sort that worked last week is broken.

**Drift from architecture decisions**

Drift is when the code stops following the plan you wrote in your ADRs. Example: a screen starts talking straight to the database, even though your ADR said never to do that.

**Unexpected functionality**

This is when the app does something nobody asked for. Example: saving an expense also sends an email that you never planned to send.

**Poor user experience flows**

This is when the steps a user takes are confusing or too long. Example: it takes five taps just to add one expense.

**Poor UI styles**

This is when the look of the app is off. Example: the buttons are out of line, or the text is cut off on a phone.

**Performance issues**

This is when the app is slow, or it slows down when a lot of people use it. Example: the list takes ten seconds to load once there are a hundred expenses.

**Errors**

An error is when the app shows an error message or crashes. Example: a wrong date makes the whole screen go blank.

**Integrations**

An integration problem is when a link to another system fails. Example: the login service says the user is signed in, but the database has no account for them yet.

## Relying on Requirements for Proper QA

[image not saved]

### How Do Requirements Affect the Success of Quality Assurance?

QA can only check what the requirements spell out. When the requirements are clear, you know what to test and what counts as a pass. When they are missing or fuzzy, QA is left guessing. So strong requirements are the base that all good QA is built on. Here is how each kind helps QA do its job.

**Acceptance Criterion**

Acceptance criteria are the plain rules that say when a feature is done and correct. They give QA a clear pass or fail line to test against. Without them, no one can agree on whether a test passed.

**BDD Scenarios**

BDD scenarios write each path as Given, When, Then. QA turns each one into a test, by hand or as an autotest. They make sure the test checks the exact behavior the team agreed on.

**Use Case Scenarios**

Use cases list every path a person can take, the happy ones and the ones that go wrong. They show QA all the cases to test, not just the easy path. This is how QA catches the edge cases.

**Prototypes**

Prototypes show what each screen and flow should look like and do. QA checks the built app against them. They make it easy to spot a screen that looks wrong or works wrong.

**Technical Architecture ADRs**

ADRs record the technical decisions and the rules the code must follow. QA uses them to check the app was built the way the team decided. They help QA catch drift, when the code stops following the plan.

**Test Case Scenarios**

A test case scenario is one exact check, with the setup, the steps, and the result you expect. QA runs it and compares the real result to the expected one. A match is a pass, and a mismatch becomes a bug ticket.

## Whats the Difference Between Test Cases and BDD and Use Cases?

[image not saved]

**BDD**

Describe the conditions and the expected behavior of users / system but do not track results

**Test Cases**

Provide the step by step sequence to follow to perform a QA test AND track the results

**Use Cases**

Provide the steps that the system and users take when performing a system task

**BDD and Test Cases**

Both describe pre-conditions and expected results

**Use Cases and BDD**

Both describe system behavior and user behavior

**Use Cases and Test Cases**

Both have step-by-step sequences

**All 3**

Are used for quality assurance testing

## QA Test Case Scenarios Step by Step

[image not saved]

**QA Test Case Scenarios Step by Step**

1. **Start with the acceptance criterion.** Pick one feature. Write the plain rule that says when it is done and correct. Every test starts here.
2. **List the use cases.** Write the happy path, where everything goes right. Then write the non-happy paths, like a blank amount or a logged-out user.
3. **Write each use case as a BDD scenario.** Put each path into the Given, When, Then shape, so everyone reads it the same way.
4. **Turn each BDD scenario into a test scenario.** Add the pre-conditions, the exact steps, and the expected result, so anyone can run it the same way.
5. **Run it and write down the actual result.** Run the test. Mark it pass or fail. Write down what really happened.
6. **File a bug ticket for each failure.** For every fail, write a bug ticket with the steps to reproduce, the expected result, and the actual result.

## Anatomy of a Test Case

[image not saved]

**Scenario**

Describe the overarching situation (the use case) that this test case covers. Include the specific audiences that relate to the scenario as well.

**Pre-conditions**

The setup for the test. Name what must already be true before you start, like an admin who is logged out and on the login page.

**Steps to Follow**

The exact actions to take, in order, so anyone can run the test the same way and get the same result. Keep each step to one simple action.

**Expected Results**

What should happen if the app works correctly. This is the line you check the real result against, so write it clear enough to mark a plain pass or fail.

**Results Table**

Where you record what really happened for each test and mark it pass or fail. A match passes. A mismatch is a fail, and each fail becomes a bug ticket.

**Pass Percentage**

Provide the number of passed scenarios over the number of failed scenarios in a given release to show a high level rate of success for the result.

## QA Pro Tips

[image not saved]

**Here are some Pro Tips for QA**

**Test on Different Browsers**

Check the app on Chrome, Safari, Edge, and Firefox, not just the one you use. Each browser reads the code a little differently, so a page that looks perfect on one can break on another. Your users are spread across all of them.

**Test on Different Devices and Systems**

Try the app on a phone, a tablet, and a computer, and on both Apple and Android or Windows. Screen sizes and systems behave differently, so a button that works on your laptop may be cut off or dead on a phone.

**Try to Break the App on Purpose**

Do not just walk the happy path. Enter bad data, tap too fast, leave fields blank, and go backward. Real users do strange things, so it is better that you find the weak spot before they do.

**Always Document the Steps to Reproduce**

Write down the exact steps that led to the bug, every time. If you cannot show how to make the bug happen again, no one else will see it or understand how to fix it. The steps to reproduce are what turn "it is broken" into something a developer can actually solve.

## DevOps

[image not saved]

### What is DevOps?

DevOps stands for Development Operations.

It’s is a way of working where the people who build the app and the people who run it work as one team, with no wall between them. In the old way, one group wrote the code and then handed it off to another group to launch it and keep it running, and problems fell into the gap between them. DevOps removes that wall. The same team builds the app, tests it, launches it, and watches it in the real world, and they share both the credit and the fixes. Teams use it because it lets them ship small changes often and safely, instead of saving up one big risky release. It matters most for large company teams, where many people touch the same app and a slow, messy launch can cause real harm. How it works is simple to picture. A developer writes code, tests it, and pushes it. Automatic checks run to catch problems, and only code that passes gets merged and sent to users. Because teams ship so often, testing and quality are built into every step instead of being saved for the end. The steps below show how this flows on a real product team.

### DevOps Process on Product Teams

Credit: Martin Fowler’s Practical Test Pyramid

1. **Develop the Code** (BUILD). A developer codes the feature on their local computer, either with Claude Code, some other AI tool, or their human brain.
2. **Test on Your Own Computer** (TEST / MANUAL TESTS). The developer performs QA checks on the code, and performs the right QA test based on the type of work being done.
3. **Push the Code to the GitHub Repo** (INFRASTRUCTURE). The developer pushes the new code base with a new “Push” to their GitHub Repo.
4. **Pull Request Created** (INFRASTRUCTURE). The GitHub turns this into a “Pull Request”. New code is ready to be “merged” into the Production code (that means, live code).
5. **GitHub Performs Scripted Quality Checks (CI)** (INFRASTRUCTURE). This step is automated with scripts checking every Pull Request. Large development teams can’t rely only on humans to ensure that nothing goes to production with bugs.
6. **5a. If Pass, MERGE the Code to Production (CD)** (DEPLOY / AUTOTESTS). Run the test. Mark it pass or fail. Write down what really happened.
7. **5b. If Fail, DO NOT MERGE** (TEST AGAIN). Prevent the code from going into production, or else there will be catastrophic bugs, failures, or security breaches. Send it back.
8. **Perform Manual Testing** (MANUAL TESTS AND AUTOTESTS). Human beings and robots need to test the code once it merges into the production environment.

## CI / CD

[image not saved]

### What is CI / CD?

CI/CD is how a team gets code from a developer’s computer to real users safely and often. It stands for Continuous Integration and Continuous Delivery, and it is really two ideas that work together. Continuous Integration, the CI part, means every person on the team merges their new code into one shared copy often, usually many times a day. Each time code is added, the system automatically builds the app and runs the tests, so if something breaks, the team finds out in minutes instead of weeks. Continuous Delivery, the CD part, means the app is always kept in a state where it could go live at any moment, so releasing stops being a big scary event and becomes a simple choice, often just the push of a button. The reason teams do this is speed with safety. Small changes go out all the time, each one is checked by automatic tests before it reaches users, and a problem is easy to spot and undo because the change was small. It matters most for large teams, where many people touch the same app, because without it their work would pile up and clash in one giant, risky release. In this class, your CI/CD happens at your GitHub repo, which runs the checks, and Vercel, which deploys the app.

### Benefits of CI / CD

Ship one feature at a time, continuously

“CI”: Continuously Integrating Code From Multiple People!

Reduce total bugs over time

“CD”: Continuously Delivering Code to Production!

Reduce human error in the software release cycle

Fix bugs faster

### The Old Way: Only Humans Check, and Release a Bunch of Features at Once

Deliver ALL Features at once (Triggered by a Human)

Integrate all features at once, only when they are ready

All features must be ready to be published in order for them to all be shown by customers at once. This is triggered by a human being.

A QA team rigorously tests every single feature going into a giant “release” of software. If one of the features fails, the whole release waits. They send it back to the developers to fix before we send the giant release to the public.

(Diagram flow: DEV builds “ONE RELEASE” of giant amounts of code changes, a QA team checks every Feature as Pass or Fail, and only when all pass does a human throw the Deploy switch to send it to the Web Server, Client, and Database Server.)

### The New Way: No Humans Involved, and Release One Feature at a Time, Continuously

Integrate Features into the Code Base Continuously (Without Humans!)

Deliver Features Continuously, one at a time, to Customers (Without Humans!)

Whenever a developer pushes code to GitHub Repo, there are scripts that run checks on the code. The scripts check for rules that must be followed. The rules are set by the technical architect to enforce standards. If the code does not pass the check, then it definitely should not be seen by customers! There may be a lot of bugs. The entire system might blow up.

When the code packages pass the quality check, they individually get delivered immediately to customers. They get deployed to the servers, the ovens, and the browser code. No one ever has to “release” a giant set of features all at once! Hundreds of code changes can individually go live in a single week.

(Diagram flow: each Feature hits a CI Check run by GitHub “Actions”; a Fail is sent back, a Pass is deployed on its own to the Web Server, Client, and Database Server.)

This week you are going to build and launch the app that lets people with ADHD budget wisely and effectively. You will turn the product specifications you wrote in Week 2 into a real, working web app that anyone can open on the internet. Every student builds the entire MVP #1 this week.

**Summary**

Now it’s time to build and ship! Your product requirements from Week 2 are going to become a reality with Claude Code. You will build a three-tier web app. The screens are built with Next.js and Material UI. The server code runs on Vercel. The database runs on Supabase. You do not have to build or run your own servers. Vercel and Supabase host them for you.

**Standard Residency - Objective**

Take the product specifications you made in Week 2, and build the entire MVP #1 of the ADHD Budgeting App with Claude Code. Use Next.js with the Material UI design system for your screens. Host the app on Vercel. Store the data in Supabase.

- The entire MVP #1, built and fully functioning
- A working database in Supabase
- People can sign up and log in, and each person sees only their own information
- At least three ADRs in docs/adr
- A database diagram
- The app is live on Vercel
- A filled-out Submission Template
- Advanced homework: test the live app with 1 to 2 real people, write up what you learn, then code and launch a new version.
