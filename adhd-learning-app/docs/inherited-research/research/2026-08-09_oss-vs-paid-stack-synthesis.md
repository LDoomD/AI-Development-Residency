## Executive summary

The three prior research passes already answered "open source or paid" for two of four stack layers: **zero** open-source options in ADHD-productivity tooling, a **real** open-source split in notes/PKM/SRS (Obsidian is the one proprietary piece already accepted, Anki/Logseq/Excalidraw are genuine OSS). This brief adds the fourth and final layer — the **AI tutor / LLM layer** — and then asks the question none of the three prior docs asked: what does the *whole stack* cost, where does it lock in, and what does it cost to get back out.

**Headline finding: the AI tutor layer is the one place open-source-maximalist is a real option — worth naming even though it isn't verified here.** Self-hosted models (Ollama/llama.cpp running Llama, Qwen, or Mistral open weights) and open orchestration frameworks (LangChain, LlamaIndex, DSPy) all carry genuinely permissive licenses, and the orchestration tooling is mature enough to build an examiner/tutor loop with. Whether the underlying models are good enough for this project's specific mastery-gate task is a separate and unanswered question — the grading table below deliberately holds every framework/runtime claim at "Moderate — not re-verified this pass" rather than asserting it as settled fact, and this summary should be read at that same confidence level. The build-plan's own evidence floor (CSAL AutoTutor, n=252) and its Examiner-first build order both depend on Claude's specific reasoning/instruction-following quality for the mastery gate to hold. Nothing in the open-source model landscape was benchmarked against that floor here; substituting a local 7–13B model changes the floor without re-testing it.

**Recommendation: hybrid.** Notes + canvas + review stay exactly where `build-plan.md` put them (Obsidian + Anki, near-zero exit cost, no vendor dependency). The AI tutor layer runs on the **Claude API directly** (not Managed Agents — this system doesn't need a hosted sandbox or persistent server-side agent, and the API is very likely cheaper for a single-user tool, though Managed Agents' actual pricing was not pulled into this brief for a direct comparison — see caveat below), because the Examiner is the one component this project already graded **High** and it is not a place to introduce unverified quality risk. Reserve local/open-source LLM tooling as the **exit path**, not the primary path — the orchestration code should be written thin enough (a handful of `messages.create()` calls, not a framework-locked agent graph) that swapping API for Ollama later is a model-string change, not a rewrite.

**Where this sits in the locked architecture:** this brief uses "AI tutor layer" as shorthand for the Examiner/tutor logic that runs inside the project's existing locked three-layer architecture (universal retrieval+spacing layer / ADHD-support layer / subject-type router) — it is not proposing a new, separate architectural layer. "Layer" is used here in the cost/lock-in sense (a distinct thing to price and reason about), not architecturally; a future pass should explicitly place the Examiner/tutor within the locked three-layer structure before this synthesis is merged.

## Quick-check: open-source LLM tooling landscape (AI tutor layer)

This is a light originalcheck, not a full verified survey like the prior three docs — treat every "Moderate" grade here as "worth a real research pass before the build order reaches the router/tutor phase," per `build-plan.md`'s own build order (tutor logic is step 3, after Examiner and Anki export).

| Category | Option | License / model | Self-hostable? | Grade |
|---|---|---|---|---|
| Orchestration framework | LangChain / LangGraph | MIT | Yes — pure Python, no server | Moderate — widely known to be MIT; not re-verified this pass |
| Orchestration framework | LlamaIndex | MIT | Yes | Moderate — same caveat |
| Orchestration framework | DSPy | Apache-2.0 | Yes | Moderate — same caveat |
| Local model runtime | Ollama | MIT (the runtime) | Yes, by design | Moderate — runtime license MIT; the *models* it serves (Llama, Qwen, Mistral) carry their own separate licenses, several with use-based restrictions (Llama's is not OSI-approved open source despite "open weight" framing) |
| Local model runtime | llama.cpp | MIT | Yes | Moderate |
| Managed self-host serving | vLLM | Apache-2.0 | Yes (needs a GPU box) | Moderate |
| Anthropic-official layer | Claude API (`claude-opus-5` / `claude-sonnet-5`) | Proprietary, usage-metered | No — API-only | High — pricing checked against the `claude-api` skill's cached Anthropic pricing reference (dated 2026-06-24; see table below) |
| Anthropic-official layer | Managed Agents (hosted sandbox + orchestration) | Proprietary, beta | No | High that it exists and is priced separately from raw API — not needed for this project's shape (single-user, no persistent multi-day agent, no sandboxed tool execution beyond file writes Obsidian already handles). Not priced in this brief — see caveat below. |

**The load-bearing distinction the prior three docs didn't need to make, and this one does:** in the PKM survey, "open source" meant *the app itself* was forkable. In the AI-tutor layer, "open source" splits into two independent axes that the PKM survey didn't have to separate — **the orchestration code** (genuinely open, low-risk to adopt either way) and **the model weights/inference** (a much bigger commitment: hosting cost, GPU/quantization tradeoffs, and — critically — no independent evidence that a locally-run open model clears the Examiner's mastery-gate bar). Conflating "the framework is MIT" with "the whole tutor layer is open source" would be the same mistake the design doc's original PKM section had to correct for FSRS: a real license fact doesn't imply the outcome evidence transfers.

**Not covered — flagged for a real research pass, not answered here:** whether any open-weight model (Llama 3.x, Qwen 2.5, Mistral) has been evaluated on anything resembling the Examiner's mastery-detection task; DSPy/LangChain's actual current GitHub star/commit-freshness numbers (last verified: not this session); Ollama's exact model-license pass-through obligations per model family; a real dollar-figure comparison of Claude API vs. Managed Agents pricing (asserted directionally above, not computed here).

Numbers are directional (single hobbyist-scale user, not enterprise), built from the pricing already verified in the three source docs plus the Claude API pricing per the `claude-api` skill's cached Anthropic pricing reference (dated 2026-06-24 — a cached reference, not a live lookup performed this session).

| Scenario | Notes+canvas | SRS | AI tutor | Rough monthly total | What you're trading |
|---|---|---|---|---|---|
| **Open-source-maximalist** | Obsidian free tier / Logseq $0 | Anki free (AnkiDroid) | Ollama + local 7–13B model, $0 API cost but needs GPU hardware (one-time $800–2000+ if not already owned, or slow CPU inference) | **$0/mo recurring**, but a real one-time hardware cost if none exists, plus unverified tutor-quality risk | Money for uncertainty — the Examiner's evidence floor (CSAL AutoTutor) has never been tested against a locally-run model in this project |

| **Hybrid (recommended)** | Obsidian free tier, no Sync | Anki free (AnkiDroid), skip AnkiMobile unless iOS review is essential | Claude API, thin orchestration, start on `claude-sonnet-5` | **~$2–8/mo**, essentially API-usage-only | Matches `build-plan.md`'s existing Obsidian-vs-Logseq logic: pay for the one component whose *quality*, not its openness, is the whole point of the system |

**Why the hybrid beats pure open-source here, stated the way `build-plan.md`'s Obsidian-vs-Logseq table states it:** that table's core move was refusing to let "open source" win by default when the open alternative loses on the property that actually matters for the loop (JSON Canvas / agent-writability). The same move applies here: local models look free and open, but the property that actually matters — Examiner reliability against a cited evidence floor — has zero verification for any local model. The cost of getting that wrong is unquantified but plausibly serious: an unverified local model could misjudge mastery in either direction inside the adaptive loop. (This brief does not claim CSAL AutoTutor documented a specific failure mechanism — only that the Examiner's evidence bar is unverified for local models; see adversarial review notes below.) A few dollars a month buys back that risk.

## Final recommendation

1. **Keep the notes/SRS decision exactly as `build-plan.md` made it.** Nothing in this synthesis changes Obsidian+Anki — both remain near-zero exit cost regardless of what the AI layer does.
2. **Run the AI tutor layer on the Claude API directly, not Managed Agents.** This project has no need for a hosted multi-day sandboxed agent — it's a single-user study loop with local file writes Obsidian/Anki already own. Managed Agents' container-per-session model is architecturally solving a problem this system doesn't have; the cost delta specifically was not computed in this brief and should be treated as a reasonable assumption, not a verified figure.
3. **Write the orchestration layer thin and framework-free** — direct `messages.create()` calls per phase (Examiner, `.apkg` generation prompts, canvas-schema generation, router), not a LangChain/DSPy agent graph. This is the one architectural choice that keeps the "moderate" lock-in risk on the AI layer from compounding: model lock-in is swappable later (rewrite the API call), framework lock-in is not (rewrite the whole control flow).
4. **Treat local/open-source models as the explicit, documented exit path, not a parallel default.** If a later research pass finds a local model that clears the Examiner's evidence bar, the thin-orchestration choice in (3) makes that swap cheap. Don't pre-pay that complexity now on unverified quality grounds.
5. **Log AI-tutor transcripts locally into the vault**, not to any remote store — this keeps the "no user data trapped in Anthropic's systems" property true by design rather than by accident, and it's the same plain-Markdown philosophy the PKM research already validated for the rest of the system.

**Caveat to carry forward, matching the pattern in every prior doc in this project:** no controlled study of any AI-tutoring layer's learning-outcome effect was run or found in this pass — this recommendation is a build-vs-buy-vs-compose judgment under the Examiner's already-cited evidence floor, not new outcome evidence for the tutor itself. Any evidence this layer has will come from the project's own Examiner validation, exactly as `build-plan.md`'s closing caveat already states for the notes/SRS layer.

## Adversarial review notes

Two independent adversarial fact-check passes were run against the original draft of this brief, in the same spirit as `specs/research/2026-08-08_adversarial-review.md`. Both passes agreed the brief was directionally trustworthy, correctly scoped (no re-citation of locked academic sources, no re-survey of already-covered tools, no contradiction of locked architectural decisions), and needed only targeted fixes rather than a rewrite. Changes made as a result:

- **Removed an invented specific failure mechanism.** The draft named "the exact CSAL AutoTutor failure mode" and described a specific mechanism (an adaptive system pressing on struggling readers instead of scaffolding them) as if it were documented in the cited source. Both reviewers independently flagged this as unsupported specificity — the locked evidence list establishes CSAL AutoTutor as an anchor/floor, not a description of a named failure mechanism. Reworded to say the risk of an unverified local model is unquantified but plausibly serious, without asserting a mechanism the source doesn't document.
- **Softened the "dramatically cheaper" Claude API vs. Managed Agents claim.** Both reviewers noted the brief never actually prices Managed Agents anywhere, so "dramatically cheaper" was an unsupported magnitude claim next to an otherwise carefully-priced document. Reworded to "very likely cheaper... though Managed Agents' actual pricing was not pulled into this brief for a direct comparison," and flagged explicitly in the Not-covered list and the final recommendation.
- **Corrected "pricing verified live this session" to reflect the actual source.** One reviewer caught that the Claude API pricing table came from the `claude-api` skill's cached reference (dated 2026-06-24, roughly six weeks stale relative to this brief's 2026-08-09 date), not a live lookup performed this session. The dollar figures themselves were confirmed accurate against that cached table by both reviewers; only the "verified live" framing overstated the rigor. Corrected throughout to cite the cached reference and its date.
- **Flagged the Obsidian Publish price as unverified rather than asserting a specific figure.** One reviewer's own suggested correction (~$16–20/mo) was not independently confirmed in this pass either, so rather than swap one unverified number for another, the line now explicitly flags Publish pricing as not re-verified this pass and points at checking current pricing before budgeting around it.
- **Tightened confidence between the executive summary and the OSS-tooling table.** The original executive summary stated as flat fact that the open orchestration frameworks "exist and are mature enough to run an examiner/tutor loop today," while the detailed table graded the same claims "Moderate — not re-verified this pass" a few paragraphs later. One reviewer flagged this as confidence whiplash on the same underlying claims. Reworded the executive summary to keep the license facts as stated but explicitly defer to the table's more hedged grading.
- **Added a one-line architectural clarification.** One reviewer noted the brief never states how the "AI tutor layer" it discusses relates to the project's locked three-layer architecture, which could read as proposing a new layer. Added a short note clarifying that "layer" is used here in the cost/lock-in sense, not as an architecture proposal, and flagging that a future pass should place the Examiner/tutor explicitly within the locked structure before merge.
- **Not changed:** the underlying license claims for LangChain/LlamaIndex/DSPy/Ollama/llama.cpp/vLLM, the Llama open-weight-vs-open-source distinction, the core hybrid recommendation (Claude API + thin orchestration + local models as exit path), and the cost-scenario table — both reviewers found these accurate or already appropriately hedged as originally written, and no changes were made to them.
